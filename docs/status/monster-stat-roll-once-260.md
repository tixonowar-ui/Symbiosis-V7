# Однократные характеристики произвольного монстра — #260

## Повторное чтение журнала NPC — 2026-11-19

При чтении журнала контрольных точек хост заново берёт строку из SQLite и
сверяет её SHA-256. Для разбора он использует общий декодер канонического
JSON. При повторном чтении той же записи события в пределах одного вызова
хост может использовать ранее проверенную неизменяемую копию. Изменение
строки или её хэша и откат транзакции видны при следующем чтении.

Прошли 19 выбранных проверок истории, повреждённых записей, отката и
канонического JSON, а также все 15 тестов контрольных точек. В двух
пятиминутных диагностических прогонах 18 ходов заняли 227,0 и 224,9 с.
Пик памяти группы за окно составил 1,41 и 1,48 ГиБ соответственно.
Снижение общего пика по этим замерам не подтверждено.

В чистом прогоне на `9c6dc9c` Windows остановила группу при достижении
лимита 4 ГиБ во время Vitest. Имя выполнявшегося теста в логе отсутствует.
По согласованию с владельцем лимит группы для двух запусков повышен до
4,5 ГиБ: для исходного интеграционного сценария замены и для чистого
`verify`. Для старта требуются 8,5 ГиБ свободной RAM и 12,5 ГиБ доступного
системного commit. Резервы во время работы составляют 4 и 8 ГиБ соответственно.
Группа получает до 25 % CPU, Vitest использует один worker, Node old-space
ограничен 3 ГиБ.

С текущей правкой исходный сценарий `npc-commit-replacement-preparation`
прошёл за 46 мин 50 с. Windows зафиксировала пик группы 4 158 709 760 байт
(3,87 ГиБ). Минимумы по выборкам составили 5,87 ГиБ свободной RAM и
9,09 ГиБ доступного commit. После выхода в группе осталось 0 процессов.

При закрытии сессии чтения причин NPC освобождаются ссылки на подготовленные SQL-запросы,
даже если вызывающий код сохранил закрытый reader. Повторное обращение через
него по-прежнему отклоняется. Порядок открытых чтений и проверки SQLite не менялись.
На этой правке прошли все 64 теста источников NPC и интеграционный сценарий
резервирования с подменой SQL и откатом. Эти проверки не измеряют память
полного сценария замены.

## Принятый body, pending ввод и квитанция

`monster-stat-roll` shared/domain kernel и host preparation переиспользуют
существующий enemy application/store, sealed ENEMY_AUTHORING causes и QUEUE.
`randomReceiptId` равен существующему owning `receiptId`; второй UUID ledger
не создаётся. Actor/campaign/attempt/origin/revisions и N+1 template/current
version проверяются до свежей генерации/записи. Seed/group strings — audit
привязки, а не публичные entity identities.

Технический nullable draft не становится принятым body автоматически.
Семь bases, масса, возраст и HP валидируются по источнику; нет clamp или
подставленных defaults. Низкий provisional ввод не забывает знания Советника.
Принятие source-valid полного MONSTER_STATS остаётся отдельным действием и
может иметь обычные source-ruled последствия. В частности D1 не объявлен
запрещённым: подтверждённое принятие такого body может забыть ACROBATICS.
До принятия pending D1,019/reopen и отказ зависимых команд знания не меняют.

Один общий predicate сравнивает pending draft с фактически принятыми четырьмя
группами inputs. Открытие018/возврат без изменений не блокирует сохранение
копии. Реальное отличие не позволяет сохранить версию или согласовать состав
до принятия body. Staging/view не могут очистить nonnull draft; только успешный
MONSTER_STATS очищает pending ввод, сохраняя квитанцию/seed/использованное право.
CUSTOM configuration own-choice preview/confirm его не очищает.

Accepted body сохраняет прежнюю закрытую grammar MANUAL/null; origin ROLL_ONCE
живёт отдельно в owning attempt ledger. Никакие поля не добавлены в старые
accepted version/receipt JSON. Новая N+1 попытка копирует механические inputs,
но начинает без материализованного seed и без spent right/receipt предыдущей.
Свой новый seed появляется после открытия018. Отмена не меняет currentVersion
и сохраняет исходную квитанцию в истории попытки.

Known command replay выполняется до fresh prepare. Ответ ROLL содержит сам
исходный семикомпонентный RandomStatsReceipt, даже после Cancel/дальнейшей
навигации. Live/историческая проверка использует фактический earlier prefix,
а не кандидат как собственное доказательство. Saved020 связывает generation
с prefix именно выбранной версии, не с поздней отменённой попыткой.

Migration0024 расширяет child cursor CHECK значениями018/019, не переписывая
applied001–23 или accepted ledger/version rows. Новый context/cause требует
полный настоящий registered24 prefix/name/checksum; удалённая24 не превращает
его в старый schema23. Настоящие исторические21/22/23 остаются читаемыми.

## 2026-11-17: SQL-reader внутри одного контекста NPC

Исходный replacement-preparation scenario на `232a724` остановлен Job limit
4 ГиБ через 2139,704 с во время COMMIT V3, до serialize/reopen. Root завершён
с кодом 125; Job и отдельный служебный helper очищены. Этот отказ сохранён во
внешнем журнале `replacement-phase-full10` и не считается успешным сценарием.

Новая правка создаёт существующий `NpcGmPrimitiveReadSession` только на время
одного `contextAt`. Рекурсивный ITEM_RESTORE, reservation readers и их вложенные
derivation prefixes получают тот же reader. Закрытие выполняется прежним
`finally`; reader не попадает в возвращаемый контекст. Чтения вне этой границы
сохраняют прежний путь. Проверки живых SQL-колонок, mutation stamp, scope,
происхождения и заголовков сохранены; numeric witness и правила lazy integer
mode не менялись. Нового глобального кэша, дополнительных SQL-writer или правил
игры нет.

Целевой файл primitive-проверок прошёл 64 сценария, включая новые отказы закрытого
reader и reader другой БД через version/inventory readers. Существующий preview
V1/N+1 прошёл отдельно. Новый тест на настоящем timed V1 проверяет повторное
чтение reservation без новых numeric witnesses, SQL-подмену, rollback,
closed/foreign-scope/foreign-DB и независимое чтение после закрытия reader.
Успешная попытка `session-context-real-scoped04`: один сценарий, 38 отфильтрованы,
14,969 с от запуска до завершения, пик committed memory Job 1 371 492 352 байта
при меньшем cap 2 ГиБ, прежнем CPU 25% и резерве RAM 4 ГиБ.

Две предыдущие попытки нового теста сохранены FAILED: финальное сравнение байтов

сохранялись. Исправленный тест проверяет байты до fault, при отказе и после всех
чтений после SAVEPOINT rollback; собственный sentinel откатывает внешнюю
транзакцию, после чего проверяются исходные байты. Assertions прежних сценариев
и бюджеты/hooks не менялись.

Это scoped-подтверждение передачи reader, а не доказательство устранения
ресурсного отказа полного replacement-сценария или прохождения merge gate.
Для окончательного committed SHA по-прежнему нужны сам исходный сценарий,
отдельный чистый цикл из пяти этапов, полный CI, независимое ревью и protected merge.
