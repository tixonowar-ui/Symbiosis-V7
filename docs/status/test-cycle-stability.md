## Проверенный локальный кандидат

В `gmSource` объединены повторные проверки очереди, admission, зеркал и
курсора внутри одного синхронного чтения. Общие данные используются только
при точном совпадении scope; чужой cursor проверяется свежим чтением.
Публичные readers, проверки до/после записи, pending RETURN и отказ без
записи сохранены. Между вызовами, записью или `await` кэш не переносится.

В локальном `readHistory` следующий шаг использует уже вычисленный SHA
предыдущего результата того же закрытого синхронного прохода. Каждое событие,
receipt, следующее состояние и сохранённый head по-прежнему проверяются;
постоянный кэш не добавлен. Целевые проверки GM composition дали 17 PASS,
локальной истории — 40 PASS; это не полные приёмочные прогоны.

Парное профилирование baseline03 → candidate01 выполнило один и тот же
исходный MIXED-сценарий с blocked/ACTIVE героями, Start и восстановлением.
Обе попытки PASS; источники каждой попытки неизменны, профили прошли проверку
целостности. Кандидат содержал оба описанных изменения вместе.

## Диагностика фаз и границы измерений

Ограниченный helper собирает wall/CPU, логические операции I/O, снимки памяти
и пересечения наблюдавшихся GC intervals для подготовки, open/migrate,
команд, reopen/restart и cleanup. Он не добавляет SQL/canonical reads или
`await`, сохраняет исходные ошибки cleanup. Переполнение, незакрытый span
или ошибка измерения делают telemetry невалидной отдельно от исхода теста.

Spans включают вложенную и фоновую работу процесса: их CPU нельзя просто
складывать. I/O counters — операции, не байты или disk wait; память — снимки,
а maxRSS относится ко всей жизни процесса. GC — сумма пересечений записанных
intervals, не полный census, не union и не причинное время остановки. Нулевое
пересечение не доказывает отсутствия GC.

В одной паре без/с helper тот же navigation-case прошёл за 5788 → 5879 мс,
а окно исполнения выбранного owning-файла с hooks — 7075 → 7050 мс
(1 case, 88 unselected). Это не полный прогон 89 случаев и не статистическое
доказательство отсутствия overhead; оба исхода сохранены.

Исходные 89 network-тестов регистрируются в пяти самостоятельных файлах:
transport/review, GM lifecycle, ACCEPT, остальные admission outcomes и PEACE.
Независимое AST-сравнение механического переноса подтвердило те же тела,
данные, бюджеты и порядок унаследованных hooks. Последующая отдельно
проверенная поправка синхронизации двух password-guard вариантов описана
ниже; assertions и бюджеты этих вариантов сохранены. Каждый файл создаёт собственный настоящий FINAL;
общие module globals изолирует штатная Vitest per-file isolation. Это
добавляет четыре root setup, поэтому выигрыш и расход памяти проверяются
полными прогонами, а не выводятся из числа групп.
Workers, retries, бюджеты, assertions и CI-настройки в этом кандидате
не изменяются.

## Разобранный отказ password-guard fixture

Первый запуск пяти групп сохранил исходный FAIL: 88 PASS / 1 FAIL из 89,
без пропусков, 515,50 с. Упал assertion о единственном сообщении в
`rechecks queued GM tab after real password verification yields`;
это не timeout. Метрики пяти групп валидны, но это выбранные owning-файлы,
а не полный репозиторий и не A/B-доказательство ускорения полного цикла.

В направленном воспроизводителе реальный password verifier позволил timer
поставить poll перед конкурирующей GM-вкладкой. Command сначала вернул один
`command.refusal` с неизменными bytes БД; затем самостоятельный poll отправил
`HOST_SYSTEM_EVENT` в тот же fixture-массив и обновил техническую проекцию.
Так наблюдение смешивало отказ команды с последующим фоновым refresh.
Этот порядок записан в направленной попытке; полные сообщения исходного
88/89 FAIL не сохранялись и задним числом не восстанавливаются.

Сигнал fixture теперь подаётся перед первым await настоящей password
verification: competing tab/trust change устанавливается до независимого
timer poll. Реальный verifier, gate, handler freshness checks, единственный
refusal и byte-no-write assertions сохранены. Scheduler/runtime не меняются.
Два исходных неинструментированных варианта дали 2 PASS / 31 unselected
(6,26 с). Повтор пяти групп перед полным gate не выполняется: окончательный
exact-SHA полный набор должен включить все 89 cases.

Направленные до/после дали соответственно исходный FAIL и PASS, но их
driver summaries отказали по отдельным условиям capture: классификации
`skipped` и ожиданию poll после cleanup. Raw результаты не переписаны.
Независимый offline audit сверил seals, все 33 identities owning suite,
порядок событий и восстановление source. Он подтвердил конкретное различие
порядка, но не наблюдал дальнейший poll после закрытия окна capture.
Попытки `204-password-directed-probe01-run` / `02-run` и отдельный audit
`review-204-password-guard-fix-independent.md` сохранены в evidence задачи;
их хеши и ссылки публикуются в итоговом PR. Эти ограничения отличаются от
исходных test outcomes и не разрешают объявлять решёнными остальные
исторические worker-startup/timeout причины.

## Границы результата и приёмка

Исторические FAIL и неполные прогоны сохранены в
[#204](https://github.com/tixonowar-ui/Symbiosis-V7/issues/204), в том числе
[worker startup clean11](https://github.com/tixonowar-ui/Symbiosis-V7/issues/204#issuecomment-6655164681).
Единая причина worker startup, CPU/HDD, GC или всех прежних timeout не
установлена. Успех изолированного случая не заменяет результат полной нагрузки.

Итоговые evidence и ссылки на замеры принадлежат PR этого изменения:
независимое ревью окончательного SHA; отдельная чистая копия с
`npm ci → import → verify → import:verify → test:e2e`; зелёный CI того же SHA,
с разбором неудачных попыток и диагностик. Фактические roster, пропуски,
ошибки, retries и границы telemetry должны быть указаны явно.
После squash merge отдельно проверяются закрытие issue и совпадение дерева
`main` с проверенным деревом. Одна зелёная попытка сама по себе не доказывает
устранение всех причин исторической нестабильности.

## Однократное решение по размеру

Владелец 2026-11-05 разрешил только для PR по #204 до 1400 удалённых
тестовых строк вместо обычных 400. Подготовленный split с метками содержит
1200 таких строк переноса/переформатирования, сохраняя все 89 случаев.
Остальные изменения и окончательный размер измеряются отдельно. Настройки
CI не меняются. Текущий classifier ошибочно относит отображаемый Git rename
к коду; в ревью и PR дополнительно приводится смысловой подсчёт тестов.
Это расхождение не используется как разрешение на удаление проверок.
