# Проверки CI

Windows job `verify` проверяет установку зависимостей, артефакты, типы,
линтер, формат, импорт, трассируемость, Vitest, кросс-реестровые связи и
production E2E. Импорт выполняется до тестов: им нужны изображения и seed,
которых нет в Git.

## Локальная приёмка и CI точного кандидата

По [ADR 0088](../adr/0088-verification-throughput-and-integration-budgets.md)
во время разработки выполняются целевые проверки и воспроизводители отказов.
После исправлений ревью, документации и traceability фиксируется окончательный
коммит. Один полный локальный прогон выполняется в отдельной чистой
копии этого точного SHA:

```bash
npm ci
npm run import
npm run verify
npm run import:verify
npm run test:e2e
```

**До push должен пройти `verify` этой чистой копии**, после её `npm ci` и
`import`. Затем remote CI может выполняться на другой машине параллельно
с оставшимися локальными `import:verify` и `test:e2e`. Merge разрешён только
после успешного завершения всех пяти локальных этапов и полного CI того же
SHA, а также независимого ревью.

Копия использует собственные зависимости, import и production-сборку E2E;
готовые `node_modules`, seed/media или dist автора не переносятся. До и после
этапов фиксируются HEAD/tree и чистота отслеживаемых файлов, команда, настройки,
время, exit code и полный лог. Проверяются фактически найденный полный набор,
отказы, пропуски и повторы; один код завершения не доказывает полноту. Каждая
попытка сохраняется отдельно. Незавершённый или прерванный прогон не является PASS.

Дополнительный полный `author verify` не обязателен: его проверки уже входят
в этот чистый прогон. После push полностью проходит CI точного SHA кандидата.
Независимое ревью с указанным scope, защита squash merge от смены HEAD и
проверка дерева `main` после merge остаются обязательными. Изменившийся кандидат
требует актуальных полного локального прогона и CI; чужой SHA и частичный
targeted PASS их не заменяют. Старые логи и исторические описания отдельных
author/clean запусков сохраняются, но не требуют второго полного локального прогона.

## Обоснованный бюджет отдельного интеграционного сценария

Агент может самостоятельно увеличить timeout тела конкретного integration
case и локальные hook/poll/wait budgets, связанные только с этим случаем,
не запрашивая отдельное разрешение владельца на каждое такое изменение.
В PR или связанном отчёте нужны:

- точные файл/имя случая и SHA, место и область действия бюджета, прежнее
  значение, сохранённый отказ и trace/log;
- фактическая длительность, выявленная причина превышения и различение тела
  сценария, setup/cleanup, зависания и ресурсного отказа;
- выбранный конечный бюджет с объяснением запаса и границ измерения;
- результат того же воспроизводителя после изменения и затем полного gate
  окончательного SHA, с сохранением первоначального отказа.

Число выбирается для измеренного случая, универсальный потолок этим решением
не задаётся. Предполагаемый запас до нового запуска не является доказанной
достаточностью. Assertions, проверяемые данные, обязательные действия и семантика
hooks сохраняются. Локальный бюджет не должен менять поведение или ожидания
других сценариев. Глобальные defaults, общие hooks и контроли, production
network timeouts, workers, retries и общий CI deadline остаются прежними;
их изменение согласуется отдельно. Изменение `.github/**` по-прежнему требует
отдельного PR с обоснованием.

Увеличение timeout не считается исправлением причины. Им нельзя скрывать
незавершающуюся операцию, неограниченный рост ресурсов, ресурсный отказ или
функциональную ошибку. Отмена по внешнему диагностическому deadline остаётся
неполным измерением, а не успешным тестом. Исторические решения о бюджетах ниже
сохранены как факты прежних изменений, не как запрет нового обоснованного case budget.

## Задержки первого релиза

Документированные умеренные задержки редких операций допустимы для первого
релиза; новый строгий latency SLA не вводится. Для такой задержки указываются
операция, измеренные условия и время, подтверждённое завершение и ограничения
измерения. Необязательные оптимизации можно отложить, не сокращая согласованный
функциональный объём и его проверки. Незавершающиеся сценарии, неограниченный
рост ресурсов, ресурсные отказы и нарушения данных, replay или privacy остаются
блокирующими. Длительность теста со всем setup/cleanup не выдаётся за задержку UI.

Меняется только общий deadline: состав и последовательность шагов, assertions,
индивидуальные test/hook/poll budgets, workers, retries, required checks и
загрузка E2E-диагностик сохраняются.

см. [issue #253](https://github.com/tixonowar-ui/Symbiosis-V7/issues/253).
[Run 42501900864, попытка 1](https://github.com/tixonowar-ui/Symbiosis-V7/actions/runs/42501900864/attempts/1)

`The job has exceeded the maximum execution time of 1h0m0s`.
Job `verify` шёл 16:50:15–17:50:21 UTC; Tests отменён, последующие validation,
E2E и upload пропущены, артефактов нет. Отмена не является PASS.

Основание для конечного запаса — полный локальный clean04 кандидата #187
`c4427834fc8741c996d9d9f8bcb2c7f69f4f0ed9`: около 122 минут от начала runner
до завершения всех пяти этапов. Verify занял 95 мин 24,687 с
(7182 теста в 285 файлах), production E2E — 24 мин 34,641 с
(45 сценариев, без повторов и отказов); воспроизводимость импорта прошла.
150 минут оставляют около 28 минут относительно этого наблюдения. Это не
точный прогноз GitHub runner и не доказательство достаточности нового лимита.

Глобальный CI-бюджет согласуется владельцем отдельно от делегированных
локальных бюджетов по [ADR 0088](../adr/0088-verification-throughput-and-integration-budgets.md);
изменение поставляется отдельным process PR. Больше времени не исправляет
функциональные ошибки, зависания или рост ресурсов и не превращает прерванный
CI в PASS. Нужен полный успешный CI точного итогового кандидата; автоматического
дальнейшего повышения лимита нет.

13:21:31–13:51:37 UTC 2026-11-03, Tests — 13:25:53–13:51:33 UTC;
Cross-registry validation и E2E не были достигнуты. Разделение проверок
и E2E на два jobs по 30 минут не устраняет этот отказ на префиксе проверок.

и сетевых операций, workers, retries, assertions, required checks и правила

## Трассируемость

`npm run traceability:verify` выполняется и в локальном `npm run verify`, и
в CI после импорта. Устаревший `docs/TRACEABILITY.md` или расхождение между
источниками и спецификацией останавливает проверку. Изменив покрытие,
перегенерируйте матрицу командой `npm run traceability` и включите её в PR.

## Воспроизводимость всего вывода

```bash
npm run import:verify
```

Команда запускает два последовательных импорта и сравнивает относительные
пути и SHA-256 каждого файла `generated/`. В сравнение входят `spec`, `types`,
игнорируемые Git изображения в `media` и SQLite в `seed`. Добавленный,
исчезнувший или побайтово изменившийся файл приводит к отказу с указанием пути.
Это проверка одинакового вывода при неизменных входах и установленных версиях
зависимостей, предусмотренная ADR 0015. Каталог не очищается: проверяется
повторный импорт в текущем рабочем дереве.

После неё CI отдельно проверяет `git status --porcelain -- generated/`.
Два одинаковых результата ещё не доказывают, что актуальный вывод включён в
коммит. Для изменений импортера пересоберите вывод и включите изменения
отслеживаемых файлов в PR.

## Пустые тестовые прогоны

`npm test`, `npm run test:coverage` и `npm run test:e2e` завершаются ошибкой,
если runner не нашёл тестов. Фиксированного ожидаемого количества нет:
набор может расти, но исчезновение всего набора не считается успехом.
`test:e2e` сначала собирает production-клиент.

## Диагностика Vitest и стоимость полного цикла

После #204 пять network suites выводят строки `SYMBIOSIS_TEST_PHASES`
в обычный лог `npm test`, в том числе в Windows Actions. JSON содержит owner,
PID, ресурсы процесса и фазы подготовки, open/migrate, handler, reopen и cleanup.
`valid: false`, незавершённые spans, overflow либо отсутствие summary означают
неполную диагностику; успешный тест не превращает её в валидное измерение.
Исходные test errors и exit code сохраняются отдельно от ошибок наблюдения.

CPU и wall включают вложенную и фоновую работу. I/O — логические операции,
GC — сумма пересечений наблюдавшихся intervals, память — снимки начала/конца.
Эти величины не доказывают дисковое ожидание, paging или полный учёт GC.
[Измерения и ограничения #204](../status/test-cycle-stability.md).

Во время исправлений сначала выполняются точные воспроизводители и относящиеся
suites. Docs, traceability и findings включаются до окончательной проверки.
На одной машине тяжёлые проверки не конкурируют друг с другом. Для кандидата
сохраняются SHA/tree, исходная команда, настройки, exit code и полный отказ.
Перезапуск без новой информации не считается исправлением.

До push завершается `verify` чистой копии; оставшиеся локальные `import:verify`
и `test:e2e` могут идти параллельно remote CI на другой машине. Merge ждёт всех
пяти локальных этапов, полного CI точного SHA и независимого ревью.
Второй полный локальный `author verify` не требуется.
Изменение source/tests требует новых результатов окончательного SHA; прежний
полный PASS не переносится на изменённый кандидат. Приёмочный набор не заменяется
целевыми тестами или диагностическим запуском с дополнительным profiler.

## Диагностика E2E и повторных попыток

В CI остаётся одна повторная попытка. Если первая попытка упала, а повтор
прошёл, Playwright отмечает тест как `flaky`. Такой прогон пока остаётся
зелёным; статус не означает, что нестабильность устранена.

HTML-отчёт сохраняется при успешном и неуспешном E2E-шаге. Для каждой
неудачной попытки сохраняются trace и screenshot, включая первую попытку
перед успешным повтором. В CI GitHub reporter также выводит диагностику
в интерфейс Actions.

1. Откройте запуск CI → артефакт `e2e-diagnostics-<номер попытки workflow>`.
2. Скачайте и распакуйте его. Срок хранения — 14 дней.
3. Откройте отчёт командой `npx playwright show-report <путь>/playwright-report`.
4. Выберите `Flaky` или `Failed`, затем нужную попытку, trace и screenshot.

Отдельный trace можно открыть командой
`npx playwright show-trace <путь>/trace.zip`. Локальные результаты находятся
в `reports/playwright-report` и `reports/e2e-artifacts`.

Если job остановился до E2E или был отменён, загрузка диагностик не
выполняется. Ошибка сборки до запуска Playwright может оставить отчёт пустым;
первичная причина в таком случае находится в логе шага E2E.
