# ADR 0018 — текущее состояние по сущностям и транзакционный checkpoint

- **Статус:** принято
- **Дата:** 2026-08-09
- **Источники:** Web UI Screen Atlas v1.2 — `entityLifecycles`,
  `stateRevision`, `projectionRevision`, `actorVisibilityRevision`; All
  Questions and Answers Registry v1.2 — `Q-CAMP-001`, `Q-CAMP-004`,
  `Q-CAMP-006`, `Q-CAMP-009`

## Контекст

Перед срезом V1 хранилищу нужны три из 19 сущностей атласа:
`localCharacter`, `campaignCharacterCopy` и `campaign`. Первые две нельзя
объединить. По `Q-CAMP-004` сохранённый вне кампании лист — шаблон с UUID, а
при добавлении в кампанию возникают отдельный `campaignCharacterId` и снимок
механического состояния. Экземпляры в разных кампаниях независимы и
автоматически не синхронизируются.

Хранилище должно переживать остановку хоста посреди операции. `Q-CAMP-009`
требует сначала атомарно сохранить текущий транзакционный checkpoint, а затем
заморозить виртуальное время, таймеры и новые команды. При открытии
восстанавливается точный подтверждённый этап: без повторного броска, двойного
списания ресурса или применения незаполненных полей. `Q-CAMP-006` дополняет
границу: подтверждённая часть операции сохраняется, неподтверждённые поля не
применяются, а отключение не удаляет персонажа.

Коды разрешаются через
[`questions-by-code.json`](../../generated/spec/qna/questions-by-code.json),
формулировки взяты из соответствующих записей
[`questions.json`](../../generated/spec/qna/questions.json) без вывода по
смыслу соседних ответов.

Это требование определяет модель хранения сильнее, чем сравнительная
производительность вариантов. Нужно явно знать, какое состояние является
последним подтверждённым, и коммитить его целиком либо не коммитить вовсе.

Атлас задаёт для каждой lifecycle-сущности собственный конечный набор
состояний. Для V1 это:

| Сущность                | Допустимые состояния                                                        |
| ----------------------- | --------------------------------------------------------------------------- |
| `localCharacter`        | `DRAFT`, `VALID`, `FINAL`, `EXPORTED`, `VARIANT`, `DELETED`                 |
| `campaignCharacterCopy` | `CANDIDATE`, `GM_REVIEW`, `PROPOSED`, `ACTIVE`, `DECLINED`, `ARCHIVED`      |
| `campaign`              | `DRAFT`, `PREFLIGHT`, `HOSTING`, `PAUSED`, `COMPLETED`, `IMMUTABLE_ARCHIVE` |

Источник наборов —
[`generated/spec/atlas/lifecycles.json`](../../generated/spec/atlas/lifecycles.json).
Порядок элементов не объявлен порядком переходов или начальным состоянием.

Тот же атлас называет три guard-ревизии дословно:
`stateRevision`, `projectionRevision`, `actorVisibilityRevision`
([`generated/spec/atlas/meta.json`](../../generated/spec/atlas/meta.json)). Их
назначение в reconnect-контракте зафиксировано в
[`docs/ARCHITECTURE.md`](../ARCHITECTURE.md), но ни один из источников не
задаёт область счётчика, начальное значение и матрицу инкрементов. Это решение
проекта, которое должен принять данный ADR.

Полной плоской схемы экземпляра персонажа в артефактах нет. `stats.json`,
`races.json`, `classes.json`, `skills.json`, `skill-requirements.json` и
`payloads.json` под
[`generated/spec/character`](../../generated/spec/character/) описывают
каталоги, ограничения и каталожные payload'ы. Они не определяют единую mutable
строку персонажа. `character/runtime-contracts.json` и
`sentient/contract.json` также содержат контракты совместимости, а не поля.
Пытаться вывести из них колонки HP, навыков, предметов, таймеров или
незавершённой операции означало бы придумать отсутствующий контракт.

Стек уже принят [ADR 0002](0002-stack.md): синхронный `better-sqlite3`. Хост —
единственный процесс-писатель; persistence-слой хранит решение domain/host, но
не принимает игровые решения сам.

## Решение

### Текущее состояние, а не журнал событий

Каждая lifecycle-сущность получает отдельную current-state таблицу. Миграция
`0001` создаёт только:

- `local_character` для `localCharacter`;
- `campaign_character_copy` для `campaignCharacterCopy`;
- `campaign` для `campaign`.

`campaign_checkpoint` — служебный снимок aggregate, а не четвёртая
lifecycle-сущность. `schema_migration` — технический реестр применённых
миграций. Seed и таблицы остальных 16 lifecycle-сущностей в `0001` не входят.

У lifecycle-таблицы есть типизированная реляционная оболочка: ID, известные из
источников связи, lifecycle-state и JSON-object текущего payload. JSON хранит
логический artifact-shaped снимок; его игровую структуру и значения проверяет
domain до вызова persistence. SQL проверяет только структурную границу —
корректный JSON-object.

`campaign_character_copy` хранит отдельный `campaignCharacterId`, FK на
кампанию, исходный UUID как provenance и независимый механический payload.
`sourceUuid` не является FK на `local_character`: исходный лист может
находиться на устройстве игрока и не обязан присутствовать в локальной
библиотеке хоста. Пара `(campaignId, sourceUuid)` уникальна: `Q-CAMP-004`
разрешает одному исходному листу породить экземпляры в разных кампаниях, но
запрещает дважды импортировать его в одну. FK кампании не каскадирует
физическое удаление: кампания имеет lifecycle-состояние
`IMMUTABLE_ARCHIVE`. Отдельно `Q-CAMP-006` запрещает считать отключение
основанием для удаления персонажа.

Кампания может существовать без строк `campaign_character_copy`. Это следует
из `Q-CAMP-001`: вместимость 1–5 — максимум одновременно активных персонажей,
а создать и готовить кампанию можно при нуле. Сам диапазон вместимости и
условия старта остаются игровыми правилами domain и в эту схему не входят.

Таблицы создаются в режиме SQLite `STRICT`. Формат UUID внутри `TEXT` пока не
проверяется SQL: артефакт задаёт семантику идентичности, но не задаёт
каноническое текстовое представление. Persistence сохраняет переданный ID
дословно; контракт его создания относится к shared/domain.

### Lifecycle-state

В каждой lifecycle-таблице состояние — отдельная `TEXT NOT NULL` колонка с
собственным inline `CHECK (... IN (...))`. Литералы выше замораживаются в
`0001`; миграция не читает актуальный `lifecycles.json` во время исполнения.
Иначе новая поставка артефакта молча изменила бы смысл уже применённой
миграции.

Начального `DEFAULT` нет: атлас перечисляет множество допустимых состояний, но
не объявляет первый элемент начальным. Состояние всегда передаёт вызывающий
слой. Новое состояние lifecycle требует следующей forward-миграции, которая
пересобирает соответствующую таблицу с новым `CHECK`; старую миграцию не
редактируют.

Отдельная lookup-таблица состояний не используется. Добавление строки в неё
было бы изменением разрешённого автомата через данные, в обход новой миграции
и ревью ADR.

### Область и инкременты ревизий

Тройка ревизий хранится на aggregate root:

- `local_character` — корень автономного локального листа;
- `campaign` — корень кампании, включая её `campaign_character_copy` и
  checkpoint;
- `campaign_checkpoint` повторяет точную тройку кампании, которую фиксирует.

Отдельной тройки на каждой campaign-copy нет: reconnect восстанавливает один
согласованный снимок кампании, а не пытается вывести его ревизию из нескольких
независимых счётчиков дочерних строк. Изменение `campaign_character_copy`
считается изменением aggregate `campaign` и двигает тройку кампании по матрице
ниже.

Каждая ревизия — `INTEGER` от `0` до `Number.MAX_SAFE_INTEGER`; начальное
значение `0`. Верхняя граница сохраняет точное представление в Node.js и
будущем JSON wire-контракте. Достижение границы — явный отказ, а не потеря
точности.

Инкременты независимы, но связаны следующим контрактом:

| Результат одной подтверждённой транзакции                                      |                                      `stateRevision` |     `projectionRevision` | `actorVisibilityRevision` |
| ------------------------------------------------------------------------------ | ---------------------------------------------------: | -----------------------: | ------------------------: |
| Изменилось авторитетное состояние aggregate                                    |                                                 `+1` | если изменилась проекция | если изменилась видимость |
| Изменилась только сериализованная проекция роли/места                          |                                                  `0` |                     `+1` | если изменилась видимость |
| Изменилась observer × actor visibility                                         | `+1`, если изменилось authoritative state; иначе `0` |                     `+1` |                      `+1` |
| Чтение, отказ валидации, idempotent/no-op replay, чистое обновление checkpoint |                                                  `0` |                      `0` |                       `0` |
| Откат транзакции                                                               |                                                  `0` |                      `0` |                       `0` |

`stateRevision` увеличивается один раз на логическую транзакцию, а не один раз
на изменённую SQL-строку. Изменение actor visibility всегда меняет
сериализованную проекцию, поэтому `actorVisibilityRevision +1` без
`projectionRevision +1` отклоняется. Persistence применяет явно переданную
матрицу изменений и проверяет эту связь; он не решает, видит ли роль игровое
поле.

API принимает только флаги `stateChanged`, `projectionChanged` и
`actorVisibilityChanged`, сам выполняет каждый `+0`/`+1` и возвращает
фактическую тройку через `UPDATE ... RETURNING`. Готовые следующие значения
счётчиков передать нельзя. Условие
`actorVisibilityChanged => projectionChanged` проверяется до записи.
Истинность флагов проекции и видимости остаётся ответственностью host/domain.

Автоматические `UPDATE`-триггеры ревизий не используются: SQL видит изменение
строки, но не может отличить новую авторитетную семантику от служебной записи
checkpoint и не знает, изменилась ли сериализованная role projection.

### Транзакционный checkpoint

Для каждой кампании хранится один последний подтверждённый
`campaign_checkpoint`: валидный JSON-object полного aggregate snapshot и
точная тройка ревизий. Это авторитетный recovery-envelope после остановки;
current-state таблицы — согласованное query-представление того же коммита.
Resume сначала сверяет тройку checkpoint с `campaign`; отсутствие checkpoint
у возобновляемой кампании или несовпадение ревизий — fail-closed. Новая
кампания до первого pause/close может существовать без checkpoint.

Внутренние поля снимка не раскладываются по придуманным колонкам: будущие
таблицы операций, бросков, боя, времени и таймеров будут добавлены по своим
артефактам, а snapshot уже может сохранить их форму без изменения
checkpoint-механизма.

Snapshot не принимается от вызывающего слоя готовой JSON-строкой. После
записей callback persistence внутри той же транзакции читает `campaign` и все
её `campaign_character_copy`, сортирует копии по ID и сам строит
детерминированный recovery-envelope из реляционной оболочки и текущих payload.
При resume тот же builder пересобирает query-представление; несовпадение с
сохранённым JSON отклоняется. Поэтому stale snapshot нельзя пометить текущей
тройкой только переданным снаружи значением.

Persistence выполняет в одном синхронном `BEGIN IMMEDIATE`:

1. все записи подтверждённой части операции в current-state таблицы;
2. один согласованный инкремент ревизий aggregate;
3. замену текущего `campaign_checkpoint` снимком с полученной тройкой.

Исключение или нарушение ограничения откатывает все три шага. Неподтверждённые
поля вообще не передаются в эту транзакцию. Повторная запись того же
подтверждённого снимка допустима и сама по себе ревизии не меняет. WAL —
механизм журналирования SQLite, а не application checkpoint: только явная
транзакционная граница выражает «подтверждено» из `Q-CAMP-009`.

### Остальные 16 lifecycle

Оставшиеся наборы принадлежат `deviceAndLocalSeat`, `group`, `npc`,
`enemyTemplate`, `item`, `symbiont`, `effect`, `longRest`, `combat`,
`combatActor`, `rollRequest`, `command`, `soundtrackContext`,
`guardianHostCapture`, `chimeraDevouring` и
`plagueDoctorInfectionRegistry`. Они получают отдельные current-state таблицы
следующими forward-миграциями: собственный ID/FK envelope, собственный
замороженный lifecycle `CHECK` и artifact-shaped JSON payload.
Campaign-scoped сущности участвуют в тройке aggregate `campaign`; сущность с
самостоятельным локальным aggregate получит тройку на своём корне.

Так добавляются новые таблицы и связи, но не меняются модель, `0001` или
checkpoint-протокол. Конкретные поля и принадлежность выводятся в задаче,
которая добавляет сущность; данный ADR не предрешает отсутствующие в
артефактах связи. Форму checkpoint версионирует общая последовательность
`schema_migration`: миграция, которой нужна новая форма snapshot, в той же
транзакции преобразует существующие JSON-checkpoint. Отдельное придуманное
поле версии payload для этого не вводится.

### Миграции и режим SQLite

Миграции имеют неизменяемые `{ version, name, sql }`, нумеруются подряд,
применяются только вперёд и записываются в `schema_migration` вместе с SHA-256
точной UTF-8 строки `sql`. При повторном открытии совпавшая применённая
миграция — no-op. Неизвестная версия, пропуск, изменившееся имя или checksum —
явная ошибка. Частично существующая схема не маскируется через
`CREATE TABLE IF NOT EXISTS`.

При bootstrap отсутствие `schema_migration` допустимо только в БД без
пользовательских таблиц. Runner в одной транзакции создаёт технический реестр,
выполняет SQL `0001` и записывает строку самой `0001`; ошибка откатывает и
реестр, и domain-таблицы. Каждая следующая миграция так же объединяет свой SQL
и запись метаданных одной транзакцией.

Каждое файловое соединение открывается и затем проверяется с режимами:

- `journal_mode = WAL`;
- `foreign_keys = ON`;
- `synchronous = FULL`.

WAL выбран при одном writer, потому что один writer не означает одного
reader: host обслуживает запросы и строит проекции ролей. Reader в WAL
фиксирует последнюю commit-frame и продолжает видеть согласованный snapshot,
пока в журнал добавляются следующие транзакции. Проверенный вместе с
закреплённым драйвером исходник SQLite прямо описывает несколько одновременных
reader snapshot; README `better-sqlite3 13.0.3` отдельно рекомендует включать
WAL.

Для `:memory:` ожидаемый journal mode — `memory`; `foreign_keys=ON` и
`synchronous=FULL` действуют без исключений. `FULL` выбран из требования
`Q-CAMP-009` о сохранённом checkpoint: `NORMAL` в WAL не синхронизирует
обычный commit, поэтому успешный ответ хоста мог бы опередить durable запись.
Единственный writer делает дополнительную синхронизацию приемлемой; это не
попытка лечить конкурентную запись, которой по контракту нет.

Утверждения проверены 2026-08-09 двумя локальными Node probe на закреплённых
`better-sqlite3 13.0.3` и SQLite `3.53.4`. File-backed probe открыл временный
путь, выполнил `pragma('journal_mode = WAL', { simple: true })`, включил и
прочитал обратно `foreign_keys`/`synchronous`, сделал заведомо неверный FK и
бросил исключение после первой записи `db.transaction(...)`; файл и sidecar'ы
были удалены после закрытия. In-memory probe создал таблицу:

```sql
CREATE TABLE probe (
  lifecycle_state TEXT NOT NULL CHECK (lifecycle_state IN ('DRAFT')),
  payload_json TEXT NOT NULL
    CHECK (json_valid(payload_json) AND json_type(payload_json) = 'object')
) STRICT;
```

Затем он отдельно попытался записать `UNKNOWN`, сломанный JSON `{` и JSON-array
`[]`. Получены результаты:

- файловый запрос `journal_mode=WAL` вернул `wal`, `foreign_keys=ON` — `1`,
  `synchronous=FULL` — `2`;
- несуществующий FK был отклонён;
- исключение после первой записи транзакции оставило `0` строк;
- для `:memory:` запрос WAL вернул `memory`;
- `STRICT`-таблица приняла один валидный object и отклонила неизвестное
  lifecycle-state, сломанный JSON и JSON-array с
  `SQLITE_CONSTRAINT_CHECK`;
- исходник поставленной SQLite поясняет: в WAL `NORMAL` не выполняет sync при
  обычном commit, а `FULL` синхронизирует WAL после каждого commit. Проверены
  `node_modules/better-sqlite3/deps/sqlite3/sqlite3.c`, строки 60244–60253 и
  63273–63281; reader snapshot — строки 67621–67636.

Настройка не полагается на compile-time defaults драйвера: эффективные значения
читаются обратно, несовпадение останавливает открытие БД.

## Обоснование

Current-state таблицы представляют доступное для запросов состояние, а
checkpoint однозначно задаёт recovery-envelope того же подтверждённого
коммита. SQLite-транзакция даёт единственную границу «всё либо ничего» для
сущностей, ревизий и checkpoint. Это выполняет `Q-CAMP-006`/`Q-CAMP-009` без
второй, отсутствующей в артефактах модели событий.

Отдельные таблицы сохраняют сильные ограничения именно там, где источник их
задаёт: FK кампании, уникальность provenance внутри кампании и разные наборы
lifecycle-state. JSON payload не является generic fallback: неизвестное
lifecycle-state, неверная связь и невалидная структура JSON отклоняются. JSON
лишь не превращает ещё не определённые игровые поля в выдуманную SQL-схему.

Отвергнутые альтернативы:

| Вариант                                    | Почему отклонён                                                                                                                                                                                                 |
| ------------------------------------------ | --------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| Event sourcing                             | Артефакты не задают vocabulary событий, порядок, преобразование старых версий и replay-контракт. `Q-CAMP-009` всё равно требует точный snapshot, поэтому журнал добавляет выдуманную модель и новый путь отказа |
| Одна generic-таблица всех сущностей        | Ослабляет entity-specific FK, `UNIQUE` и lifecycle `CHECK`; состояние одной сущности можно ошибочно записать другой                                                                                             |
| Lookup-таблица lifecycle-state             | Строка данных молча расширяет разрешённый автомат без forward-миграции                                                                                                                                          |
| Только application-валидация lifecycle     | Прямой SQL может сохранить неизвестное состояние, что нарушает fail-closed                                                                                                                                      |
| Полностью плоские игровые колонки          | Полного mutable-instance контракта персонажа и checkpoint нет; колонки пришлось бы придумать                                                                                                                    |
| Независимая тройка на каждой campaign-copy | Не определено, как получить одну согласованную reconnect-ревизию кампании из нескольких дочерних счётчиков                                                                                                      |
| Триггеры, инкрементирующие любой `UPDATE`  | Не знают, изменилась ли семантика проекции/видимости, и ошибочно считают служебные/no-op записи                                                                                                                 |
| Копия файла БД как checkpoint              | Не выражает подтверждённый этап операции и требует координации с WAL; транзакционный snapshot уже решает задачу                                                                                                 |
| Rollback journal (`DELETE`)                | Корректен при одном writer, но не даёт reader snapshot WAL для параллельных запросов/проекций host; выигрыш от отсутствия sidecar'ов не перевешивает это ограничение                                            |
| WAL + `synchronous=NORMAL`                 | Обычный WAL commit не синхронизируется; подтверждение могло бы быть выдано раньше durable checkpoint                                                                                                            |

## Последствия

- В V1 появляются только три lifecycle-таблицы, revision scopes, текущий
  campaign checkpoint и технический реестр миграций. Seed остаётся issue #6.
- Неизвестное lifecycle-state, невалидный JSON, неверный FK, повторный source
  UUID в одной кампании и недопустимый инкремент ревизий отклоняются явно.
- Хранилище не проверяет выбор расы, класса, навыков, вместимость и переходы
  lifecycle. Это игровые решения domain, а не SQL.
- Current-state модель не даёт историю или replay событий. Если продукту
  понадобится аудит, он добавляется отдельной моделью и ADR, а не меняет
  источник восстановления.
- JSON payload хуже индексируется, чем плоские колонки. Индексы и
  нормализация добавляются только после появления artifact-backed поля и
  реального query path.
- Checkpoint дублирует текущее состояние и ревизии. Это осознанная цена
  независимого, точного restore envelope.
- Изменение lifecycle-набора требует новой миграции с пересборкой таблицы;
  применённая `0001` остаётся неизменной.
- `synchronous=FULL` дороже `NORMAL`, но сохраняет checkpoint до подтверждения
  commit. Один host-writer ограничивает стоимость этой гарантии.
- WAL создаёт соседние `-wal`/`-shm` sidecar-файлы. Portable-упаковка должна
  закрывать соединение и штатно checkpoint'ить WAL, а не копировать один
  основной файл открытой БД.
- In-memory тесты видят `journal_mode=memory`, поэтому не выдают отсутствие
  `wal` за ошибку; файловое production-соединение обязано вернуть `wal`.
