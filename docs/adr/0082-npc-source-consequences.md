# ADR 0082 — Календарь, наследие и пулы исходного NPC

- **Статус:** принято владельцем; решения #224, #226, #227 и #232
- **Дата:** 2026-11-06
- **Основание:** явное принятие четырёх предложений и соответствующей поставки источников
- **Дополняет:** ADR 0077, 0078 и 0081; прежние принятые ADR не переписываются
- **Поставка:** Atlas 1.15/B10; runtime и реальные controls — отдельная реализация #187

## Граница решения

Четыре пробела мешали воспроизводимо сохранить полный NPC через существующий
wizard. Этот ADR материализует именно принятые решения, а Atlas отражает их
в полях, controls, guards, preview, readback и QA. По ADR 0003 решение проекта
имеет приоритет над нижележащими источниками только в явно названных ветвях.
Предметные XLSX, Runtime Pack, остальные игровые реестры и старые ADR не
изменяются. Это не разрешение создавать вымышленную историю, RNG, XP, сцены
или generic effect handler.

## 1. Фаза алкогольного состояния — #224

CORE-110 (§5.4.3.3, стр. 96; Rules, «Реестр правил», B491:AH491) задаёт
алкоголю 5 HP в час и срок 30−Z часов; при неположительном сроке эффект не
возникает. TIME-004/005/017 и Effects/12 требуют точных startsAt и tickSchedule,
но не выбирали фазу первого часового тика. Q-CORE-029 исключает пищевое
отравление; Q-CORE-062/063 сохраняют точное календарное время.

Для **нового** алкогольного состояния первый тик назначается ровно на
`startsAt + 60 минут`, следующие — через полные интервалы по 60 минут.
Нет немедленного урона и округления к календарному часу. Тик, назначенный
ровно на expiresAt, исполняется в фазе ticks перед expiry по AQA-024.
Если 30−Z<=0, результат NO_EFFECT: нет effectInstance, tick или ложного
календарного события. Immunity/response и прочие условия CORE-110 сохраняются.
Правило не распространяется на другие periodic effects.

NPC-016 получает выбор алкогольного состояния, обязательную причину и
показывает проверенные startsAt/nextTickAt/expiresAt либо NO_EFFECT и причину.
Начало — подтверждённое PRE_START_INITIAL или CURRENT_CAMPAIGN, а не ввод
произвольной фазы. До Start успешный COMMIT календарного состояния закрепляет
время по ADR 0078; draft/preview/отказ lock не создают. Date.now, timezone,
автоматический ход часов и выдуманный combat context не используются.

Retained instance сохраняет прежние origin, IDs, startsAt, nextTickAt и
expiresAt. N+1/restart/replay не начинают период заново. Исторический
snapshot без доказуемой фазы не дополняется предполагаемым расписанием.

## 2. Наследие Трогра — #226

SYM-076 (7.5.7.2.1, стр. 130), SYM-025 и CORE-079 задают постоянный вклад,
сохранение характеристик при удалении и порядок ограничений. Они не замыкали
повторное получение, смену основы и смену минимумов. Действуют три отдельные
величины одного lifetime ledger правила SYM-076 у носителя:

1. Необратимо достигнутая сила: L и сырой вектор `+6L` для S/D/M/Z,
   `−6L` для I/W/C.
2. Достигнутая сила, уже включённая в снятое наследие.
3. **Фактический signed snapshot** всех семи характеристик относительно
   доказанного non-Trogr basis непосредственно перед удалением.

Без прежней подтверждённой истории reached=current, и получается обычный
SYM-076. При имеющейся истории ручное снижение targetLevel в N+1 не стирает
достигнутую силу постоянного статового вклада. При повторном получении старый
snapshot участвует ровно один раз; добавляется только raw прирост достигнутой
силы сверх уже включённой. Равная/меньшая сила повторного вклада не даёт.
После этого применяются caps/minima из текущего подтверждённого состава:
Трогр, поглощённый Учитель и подавленный Советник по CORE-079 и их собственным
правилам. Обычное наличие активного Учителя не означает его поглощения.

При удалении записывается **новый фактический** signed snapshot. Он может
стать меньше по абсолютной величине из-за изменившегося min/max. Общий abs/max
старого и нового векторов запрещён: он теряет знак и текущий результат.
Изменение non-Trogr basis без Трогра не вычисляет наследие заново из raw силы.

Пример: UNITED с non-Trogr S20 и L1 имеет S25; удаление сохраняет +5.
При новой основе S10 получается S15. Повторный L1 оставляет S15, L2 добавляет
только новый raw прирост6 и даёт S21. Для I15/L3 без Учителя I1 даёт snapshot
−14; тот же L3 после поглощения Учителя имеет I4, и новое удаление сохраняет
snapshot−11.

Необратимость reached относится **только** к permanent stat ledger SYM-076.
HP20L, броня и остальные активные пассивы остаются по своим источникам и
current level, прекращаясь при removal. HP, armor, caps/minima и suppression
не становятся самостоятельным наследием. Никакая часть этого решения не
подменяет обязательные последствия поглощения и реальные composition facts.

NPC-013 сохраняет существующие controls вида, уровня, узлов, привязки и ОЭ,
а перед подтверждением показывает последствия и отдельные read-only reached,
included и signed snapshot. NPC-014/017 показывают постоянный результат.
Историю нельзя редактировать как числовой shortcut к желаемым статам.

## 3. Hunger и Regeneration — #227

MON-023/024, CQA-045, SYM-034, CQA-008 и Q-SYM-013 описывают активации и
снятия, но не разрешали неоднозначность совместного maxHP. Доступность
сочетания требует настоящих composition/development фактов: включая
MON-007 для дополнительных слотов Химеры и изученную ветвь Ткача. Поле
desired extraSlots или formal GM assignment не заменяет эти факты.

`H` — максимум из остальных актуальных источников, исключая два режима.
Итоговый maxHP равен 1000 при действующей Regeneration, иначе 2×H при Hunger,
иначе H. Это правило **только этой пары**, не общий порядок всех HP-эффектов.

Успешная активация Regeneration ровно один раз устанавливает currentHP1000;
успешная активация Hunger ровно один раз удваивает currentHP с clamp к
итоговому maxHP. Обычный пересчёт не лечит. MinHP1 и независимые двухходовые
лечения CQA-008 сохраняются. При снятии Hunger удаляется только его maxHP/stat
вклад, затем `currentHP=min(ceil(currentHP/2),newMaxHP)`. При снятии Regeneration
удаляется exact1000, maxHP пересчитывается с оставшимся Hunger, currentHP
ограничивается новым максимумом без лечения.

Не восстанавливается устаревший undo maxHP. Сохранённые таймеры лечения не
стартуют заново; одновременные окончания сохраняют AQA-024. При H300/HP200
обе последовательности активации дают 1000/1000. При двух режимах/HP800
снятие Hunger→Regeneration даёт 1000/400→300/300; обратное — 600/600→300/300.

NPC-016 вводит текущее исходное состояние с явными source instances,
prerequisites и сроками каждого режима. Это не повторная активация:
введённые текущие HP сохраняются с проверкой итоговых bounds, не удваиваются
и не лечатся при preview/COMMIT. NPC-017 показывает H, режимы, derived maxHP,
currentHP и отдельные сроки/таймеры. Реальные прошлые активации/RNG не
дорисовываются; неполный proof блокирует эту комбинацию с конкретной причиной.

## 4. Пять слотов SYM-166 — #232

SYM-166 (7.5.18.7.1, стр. 156) добавляет пять слотов навыков. CORE-081
(стр.86), CORE-165 (стр.105–106), CORE-166 (стр.105–108) и SYM-025
(стр.113) не определяли их отдельный пул и судьбу при потере источника.

Вводится один именованный lifetime пул `SYM-166` у носителя. Его capacity5
действует только при действующем Дельфине с изученным и доступным SYM-166,
иначе capacity0. START, TRAINING, W, maxPermanentWisdom и W-based everIssued
не меняются. Пять слотов не означают автоматическую выдачу пяти навыков.
GM выбирает навыки/повышения и пул оплаты; цена и требования — CORE-165.
Стоимость повышения — разница стоимости ступеней. Разные ступени одного
навыка могут использовать разные явно выбранные пулы.

Пул допускает свободный остаток. Полное заполнение START остаётся отдельным
обязательством START. Каждый charge сохраняет реальную confirmation identity,
skillKey, bonusBefore/bonusAfter, chargedSlotCost, pool и действовавшие
symbiontInstanceId/nodeRef. Новый Дельфин не создаёт новую пятёрку.

Удаление, гибель или недоступность источника меняют capacity на0, сохраняя
навыки и charges. Overfill сам по себе не удаляет и не отключает навыки,
но запрещает новые затраты этого пула. Независимая временная потеря настоящего
требования навыка по CORE-166 только отключает навык и не освобождает charges.
Постоянная потеря забывает навык и освобождает реальные затраты именно тех
пулов, которые оплатили соответствующие ступени. Reacquisition возвращает capacity5
того же пула: used5 остаётся used5/available0; после реального освобождения2
доступны2. `available=max(0,capacity-used)`, `overfill=max(0,used-capacity)`.

Достижимый пример: UNITED, все исходные статы20, один DOLPHIN L6 с полной
последовательностью узлов. Свободные оставшиеся слоты допустимы AQ2-017 /
Q-GM-SYM-005. Manual race даёт S13/D20/M10/Z10/I20/W20/C20; SYM-162 даёт I30,
W остаётся20. START10/TRAINING10; расовая «Следуя боли» CORE-004 не занимает
слот. SYM-166 может оплатить STEALTH+2 ценой2 и ACROBATICS+3 ценой3 при
подтверждённых остальных требованиях. Ожидаемые пулы не выводятся из числа
выбранных навыков и не меняют W.

NPC-014 содержит реальные controls skill/targetBonus/pool и отдельные
capacity/used/available/overfill. Preview, лист и история показывают источник
каждой ступени. NPC-013/017 показывают последствия смены состава. N+1 сохраняет
исходные charge references; старые START/TRAINING не переклассифицируются.

## Закрытая граница proof, controls и сохранения

Следующие требования технические, не новые игровые величины. Каждый ввод
закрыт по варианту: неизвестные/дополнительные/accessor поля, orphan/foreign
ссылки и несовместимые variants отвергаются. Незаполненный draft остаётся
UNSET; он может хранить промежуточный ввод, но не разрешает forward/COMMIT.

`trogrStrengthAndLegacyOrNull` ссылается на настоящий immutable composition
prefix и stat context для reached, included и signed snapshot. Все stat
блоки содержат ровно S/D/M/Z/I/W/C. Level, raw delta и результат вычисляются
из prefix; client не предоставляет самодостаточный authoritative snapshot.
При отсутствии прежнего removal нет legacy snapshot; нулевой выдуманный
removal fact не создаётся. Все последующие versions продолжают тот же ledger.

`sym166Pool` содержит capacity/used/available/overfill и реальные charges.
Затрата связывается с существующим подтверждением NPC-014, owner/attempt,
skill, ступенью и доступным source instance в точном composition prefix.
Поля capacity и cost производные, клиент выбирает только допустимый навык,
целевую ступень и pool. Проверяется каждое промежуточное повышение.

`alcoholScheduleOrNoEffectOrNull` различает отсутствие, проверенный NO_EFFECT
и ACTIVE. Только ACTIVE содержит полный существующий EffectInstance codec
с identity/owner/source/time/tickSchedule и реальным calendar anchor.
`combinedHpModesAndValidationOrNull` связывает каждый режим с его настоящим
source instance и точным current state/сроком. Partial DTO, голый Rule ID или
unchecked набор чисел не заменяет полный Effects/12 codec.

Scope/author доказываются текущей GM authority и реально сохранёнными
операциями. Preview ссылается на фактический stage/confirmation prefix,
а не будущий COMMIT. Writer формирует pending evidence после реального
выделения audit; исторический reader принимает только committed provenance.
Canonical hash сам по себе не доказывает источник. Old snapshots, FINAL,
receipts, IDs/timestamps и исторические prefixes не переписываются.

NPC-013→014, NPC-014→015 и NPC-016→017 проверяют соответствующий полный
подтверждённый ввод. COMMIT-V1 и NEW-VERSION phase=COMMIT повторно проверяют
все варианты, authority, attempt/version/source/calendar bindings и пишут
sheet/facts/checkpoint/receipt атомарно. OPEN и receipt-return не требуют
нового authoring input. Exact replay возвращает прежний receipt; stale,
foreign, changed или недоказанный запрос не пишет ничего.

UI не подменяет controls JSON editor или одной кнопкой подтверждения.
Вычисляемые ledger, schedule, HP и pool values read-only. Используются
существующие NPC forms/workflows; второй shell не создаётся. NPC-003/007
показывают сохранённый результат и историю, не редактируя прежние версии.

Atlas 1.15 сохраняет schemaVersion1.2.0, legacy filenames v1.2, 376 forms,
1721 transitions, 66 journeys, 91 requirements, 115 workflows, 2452 QA и
1283 CTA. Producer graphDigest/contentDigest, globalContracts, GM-014 и
source/workflow IDs сохраняются. Самостоятельные Rules не становятся
executable UI commands. JSON и Markdown поставляются совместно; все
затронутые workflow/CTA/transition/journey/requirement/QA mirrors согласованы.

пяти стадий и CI фиксируются в PR. Эта source-поставка ссылается на
#224/#226/#227/#232, но не объявляет runtime #187 и их controls завершёнными.
