# ADR 0096 — Передача общего компьютера при допуске и в лобби

- **Статус** — [принято владельцем 22 ноября 2026 года](https://github.com/tixonowar-ui/Symbiosis-V7/issues/297#issuecomment-7078243763).
- **Источники** — Atlas 1.24/B19 и [согласованная поставка #297](https://github.com/tixonowar-ui/Symbiosis-V7/issues/297).
- **Реализация** — [#263](https://github.com/tixonowar-ui/Symbiosis-V7/issues/263), родитель [#211](https://github.com/tixonowar-ui/Symbiosis-V7/issues/211).

## Зачем нужен переход до первой сцены

Мастер создал кампанию на общем компьютере. Первый локальный игрок создал
персонажа, принял предложение мастера и подтвердил готовность в NET-006.
Чтобы выполнить первый Start, мастер должен получить управление в NET-016.
В этот момент кампания ещё PAUSED и сцены нет. Если мастер впервые ввёл время
или изменил его, прежняя готовность устарела. Устройство снова требуется игроку.
[Основание Ready и условия Start](0073-campaign-lobby-start-source.md).

## Кому передаётся заявка

После SUBMIT устройство возвращается мастеру через завесу. В NET-017 мастер
выбирает конкретную локальную заявку и передаёт устройство её владельцу.
Хост связывает заявленный профиль с его исходным ACK, локальной вкладкой,
кампанией, технической сессией, заявкой и квитанцией SUBMIT. Хост проверяет
актуальную ревизию заявки. После публикации предложения он сверяет также
пакет, ревизию и контрольную сумму предложения. Сетевая публикация результата
может прийти до физической передачи. Частные данные получает только адресат,
подтвердивший новую завесу. До принятого допуска профиль остаётся кандидатом.
[Профили и права на оригиналы](0095-local-owner-binding-for-existing-finals.md).

| Действие на общем устройстве                                             | Доступный результат                                                                                                                                                                                                                          |
| ------------------------------------------------------------------------ | -------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| APP-003::CTA::014, вернуться до SUBMIT                                   | Кандидат возвращает устройство исходному мастеру. Действие доступно из собственной библиотеки через APP-004::CTA::002 и после выбора из NET-003::CTA::004. Записанные профиль, checkpoints и FINAL сохраняются.                              |
| NET-017::CTA::011, передать заявку адресату                              | После ACK владельцу открывается собственная NET-005 для PENDING, ожидания IN_REVIEW или предварительного отказа, NET-027 для опубликованного предложения либо NET-007 для окончательного отказа. После перезапуска проверяется та же заявка. |
| NET-005::CTA::004, возврат из ожидания или после предварительного отказа | Мастер получает свой подписанный контекст после ACK. Возврат из PENDING сохраняет заявку. Отмена разрешена прежней командой только для PENDING. При гонке с решением мастера результат определяет сохранённая requestRevision.               |
| NET-003::CTA::005, возврат после отмены                                  | Основание возврата — квитанция подтверждённой отмены собственной заявки. До получения результата команда остаётся за исходным владельцем.                                                                                                    |

Место при отказе или отмене не создаётся.                                                                           |

В режиме TARGET_OWNER_ADMISSION у получателя свежего профиля может быть
выбрано от нуля до трёх собственных FINAL. Для возврата через APP-003::CTA::014
хост проверяет действующий ACK профиля и подписанный возврат к мастеру до SUBMIT.
Пустой выбор подходит для возврата. Для APP-003::CTA::009 хост требует от одного
до трёх выбранных FINAL и проверяет актуальное право на каждый из них.

## Кому передаётся лобби

В NET-006::CTA::005 допущенный игрок передаёт устройство единственному
мастеру. До первого Start мастер попадает в свою NET-016. В NET-016::CTA::006
он выбирает конкретную допущенную локальную вкладку, после ACK открывается
её NET-006. Хост сверяет кампанию, квитанцию допуска и фактическую привязку
контроллера этой вкладки. Передача допустима при Ready и Not ready.
Ввод времени, подтверждение готовности и первый Start выполняют их владельцы
отдельными командами.

В смешанном составе любая подтверждённая вкладка устройства может передать
Ready для всего его точного набора ACTIVE. Устройство только с заблокированными
копиями не может подтвердить Ready. Если другой ACTIVE-герой позволил запустить
кампанию, действительно допущенная заблокированная вкладка со своим контроллером
сохраняет NET-006. Теперь её возврат мастеру ведёт на действующую мирную GM-001.
При выборе этой вкладки из PLY-028::CTA::003 она получает свою NET-006.
Хост сверяет подтверждённый Start, текущую кампанию и адресата. Включённые
ACTIVE-вкладки продолжают входить в свою мирную сцену по квитанции Start.
[Журнал лобби](0074-campaign-lobby-runtime.md).

## Приватность, повтор и восстановление

Все эти пути используют существующий журнал передачи и PLY-030. До показа
завесы хост отзывает выдачу прежней роли на соединениях общего компьютера,
включая фоновые подписки. Клиенты удаляют прежний экран, данные доступности,
горячие клавиши и кэш. Завеса показывает только обозначение мастера либо метку
и идентификатор адресата с необходимым непрозрачным подтверждением. Другие
установки продолжают получать разрешённые им публикации.

Перед передачей хост проверяет безопасную границу. Незавершённая команда,
выбор цели, реакция, серия или бросок блокируют переключение. На адресном
ACK хост ещё раз проверяет актуальные привязки. Только затем PLY-029
открывает определённую хостом форму. При неопределённом результате сохраняется
владелец исходной команды. При повторном открытии SQLite восстанавливаются
те же идентификаторы и квитанции. Точный повтор исторического ACK возвращает
его результат без повторной активации старой проекции.

Поставка фиксирует источники, зеркала, проверки и совместимость сохранений.
За управление на рабочих экранных формах и проверку фактических WS-сообщений,
DOM и восстановления браузера отвечает #263.
