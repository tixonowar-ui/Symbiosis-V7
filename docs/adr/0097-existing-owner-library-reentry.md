# ADR 0097 — Повторный вход владельца в локальную библиотеку

**Статус** — принято владельцем 26 ноября 2026 года для поставки Atlas 1.25/B20. [Решение #300](https://github.com/tixonowar-ui/Symbiosis-V7/issues/300).

## Почему нужен отдельный вход

Ира приняла два сохранённых FINAL в кампании А. Подтверждение адресованной передачи завершило её ожидающее продолжение. В кампании Б на том же компьютере Ира по-прежнему владеет обоими оригиналами. Все листы устройства уже могут иметь владельцев. Для просмотра библиотеки в такой ситуации требуется новая передача от действующего мастера Б. Повторять привязку листов или использовать старую квитанцию для открытия экрана нельзя. Сценарий закреплён в `QA-LOCAL-OWNER-LIFETIME`. [ADR 0095](0095-local-owner-binding-for-existing-finals.md).

## Выбор профиля

Мастер входит через CMP-009::005. После очистки мастерской проекции нейтральная APP-003 позволяет выбрать профиль по точному `targetLocalOwnerId` и видимой метке. Одинаковые метки различаются идентификаторами. Если профилю принадлежит хотя бы один локальный FINAL, хост может предложить **APP-003::015 «Передать устройство владельцу сохранённой библиотеки»**. Действие разрешено и для оригинала, созданного самим профилем с подтверждённым происхождением, и для ранее привязанного через BIND. Для собственного создания отдельная квитанция BIND не требуется.

Само появление кнопки сообщает ровно один факт — у выбранного профиля есть подходящий FINAL. На нейтральном экране отсутствуют имена и UUID персонажей, количество листов и содержимое библиотеки. Пустому профилю доступен существующий вход APP-003::013. При ожидающей передаче этому профилю в текущей кампании мастер выбирает её штатное продолжение по точному `pendingContinuationId`. Полученный ранее ACK не позволяет снова использовать израсходованный ID.

## Новая передача и подтверждение

Хост использует существующий тип `HOST_LOCAL_CANDIDATE` с отдельным основанием `EXISTING_OWNER_LIBRARY`. До выдачи шторки он проверяет идентичность установки и устройства, полномочия единственного текущего мастера, активную кампанию, профиль, наличие принадлежащего ему FINAL, безопасное состояние и текущие ревизии. При переходе между кампаниями требуется подтверждённое завершение или разрешённое освобождение контекста А. Незавершённая операция, неизвестный исход команды или непогашенная шторка блокируют переход. Отказ сохраняет исходного владельца операции и прежний контекст. Отложенные передачи других профилей сохраняются за своими адресатами и кампаниями.

Для Б выдаются новые `handoffId` и подписанный контекст возврата. Адрес связывает кампанию и текущего мастера Б, установку, устройство, профиль и его метку. На всех затронутых соединениях прежние приватные данные и подписки очищаются до выдачи шторки PLY-030. На шторке человек видит, кому передают устройство. Подтверждение остаётся явной передачей общего компьютера между участниками.

При **PLY-030::004** хост повторно проверяет текущую установку и устройство, адресованную доставку, кампанию, основание, handoffId, точный профиль, его действующие права на оригинал и ревизии. `UI-CMD-LOCAL-CONTEXT-HANDOFF-ACK` с решением `ACTIVATE_TARGET` открывает этому получателю APP-004 с текущими листами его профиля. Смена кампании, вкладка браузера, старый секрет доставки и совпадение метки не передают эти права. После сброса идентичности прежняя библиотека остаётся недоступна новой установке.

После перезапуска до ACK восстанавливается только текущая нейтральная шторка. После ACK приватную библиотеку получает соединение с текущей подтверждённой передачей. Точный повтор команды возвращает прежнюю квитанцию без смены текущего экрана. Устаревшая ревизия, подмена адресата или изменённый запрос завершаются отказом без частичной записи.

## Возврат и допуск

| Момент                       | Действия и результат                                                                                                                                                                      |
| ---------------------------- | ----------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| До открытия библиотеки       | PLY-030::008 отменяет вход. Хост выдаёт подписанную шторку возврата исходному мастеру Б. После PLY-030::006 с решением `RETURN_INITIATOR` мастер получает CMP-009.                        |
| После просмотра без заявки   | APP-004::002 → APP-003::014 → PLY-030::006. Выбрано от нуля до трёх своих листов, SUBMIT ещё не начался. Данные владельца очищаются до шторки. Действующий мастер Б подтверждает возврат. |
| Владелец хочет подать заявку | APP-004::002 → APP-003::009 требует от одного до трёх собственных FINAL. Далее действует обычный допуск с проверкой принадлежности при выборе, открытии и отправке.                       |

APP-003::014 получает новое основание только для текущего `EXISTING_OWNER_LIBRARY`. При первой привязке неназначенных FINAL устройство сначала получает выбирающий, затем профиль-получатель. Хост сверяет записанную привязку и точный действующий `pendingContinuationId` как при первом ACK после BIND, так и при его отложенном продолжении. Путь ::014 до SUBMIT этим получателям недоступен. «Позже» относится к ожидающей передаче после привязки. У свежего профиля действует подписанный возврат по B19. Новый вход в библиотеку сохраняет исходные назначения, заявки, копии, места и контроллеры. Права в прежней кампании по нему не выдаются. [ADR 0095](0095-local-owner-binding-for-existing-finals.md) · [ADR 0096](0096-host-local-admission-and-lobby-handoff.md).

Условие пустой библиотеки относится к первому входу APP-003::013. Если игрок
создал FINAL, вернул устройство мастеру до SUBMIT и снова получает его через
CMP-009::004, хост использует подписанный возврат того же профиля в той же
кампании, сверяет текущий контекст мастера и выдаёт новую шторку с отдельным ACK.
APP-003::003 также сохраняет свой прежний вход с заранее выбранными 1–3 листами
проверенного владельца. В кампании Б для открытия библиотеки по выбору профиля
действует новое основание ::015.

## Проверка и граница поставки

В двух браузерных контекстах проверяются два одноимённых профиля с разными листами, вход в Б при отсутствии неназначенных FINAL, отмена до ACK и возврат после просмотра без выбора. Проверка охватывает кадры WebSocket, DOM, дерево доступности, горячие клавиши, кэш и фоновые подписки. После повторного открытия SQLite сохраняются UUID, версии, байты и происхождение оригиналов. Исторический повтор после передачи второму владельцу оставляет активным второго адресата. Конфликт А → Б и сброс установки проверяются отдельно.

Поставка определяет источники, зеркала атласа, guards и QA. Реальный вход относится к #264, отображение принятого допуска в игровые вкладки — к #265. Для проверки смены кампании используются сохранённые состояния. Команда завершения кампании относится к #269.
