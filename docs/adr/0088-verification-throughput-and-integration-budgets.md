# ADR 0088 — Один чистый локальный gate и обоснованные бюджеты сценариев

- **Статус:** принято владельцем
- **Дата:** 2026-11-07
- **Основание:** явное решение владельца о процессе проверки и первом релизе
- **Уточняет:** процессную часть ADR 0087 и прежних описаний author/clean gates;
  предметные решения и исторические результаты не изменяются

## Контекст

Полный авторский `verify` и последующий чистый пятиэтапный прогон повторяют
один набор проверок. При длинных интеграционных сценариях это увеличивает
стоимость каждой исправленной версии кандидата. Отдельные case timeouts
также требовали повторных вопросов владельцу, хотя само обоснование можно
проверить по сохранённому отказу и измерению.

Владелец разрешил убрать обязательный дублирующий полный локальный запуск,
делегировал обоснованные бюджеты отдельных интеграционных сценариев и принял
документированные умеренные задержки редких операций для первого релиза.
Это решение о процессе, а не измеренное улучшение производительности.

## Решение

1. Во время разработки выполняются целевые проверки и точные воспроизводители.
   После исправлений ревью, docs и traceability фиксируется окончательный SHA.
   Один полный локальный прогон в отдельной чистой копии этого коммита
   выполняет `npm ci → npm run import → npm run verify → npm run import:verify → npm run test:e2e`.
   Дополнительный полный `author verify` не обязателен. До push должен пройти
   `verify` этой чистой копии после её `npm ci` и `import`. Затем полный CI
   того же SHA может идти на другой машине параллельно с оставшимися локальными
   `import:verify` и `test:e2e`. Merge ждёт всех пяти локальных этапов, полного
   зелёного CI и независимого ревью. Новый кандидат получает новые результаты.
2. Независимое ревью с честными границами прочитанного, защищённый squash merge
   и проверка дерева `main` после merge сохраняются. Результаты привязаны к SHA,
   tree и фактическому полному набору проверок; неполный или отменённый запуск
   не считается успешным. Чистая копия не заимствует зависимости или готовый
   generated/dist автора. Прежние отказы и traces сохраняются.
3. Агент может увеличить timeout тела конкретного интеграционного сценария
   и локальные hook/poll/wait budgets, связанные только с этим случаем, без
   отдельного вопроса владельцу. Он сохраняет exact case/SHA, место и область
   действия бюджета, отказ и trace/log,
   фактическое время, выявленную причину и обоснование выбранного конечного
   бюджета; затем проверяет тот же сценарий и полный окончательный кандидат.
   Общий числовой потолок этим решением не вводится. Assertions, данные,
   обязательные действия и семантика hooks не ослабляются; другие сценарии
   локальным бюджетом не затрагиваются. Глобальные defaults, общие hooks и
   контроли, production network timeouts, workers, retries и CI-бюджеты остаются
   прежними; их изменение согласуется отдельно. Изменения CI по-прежнему идут
   отдельным PR.
4. Больший timeout не означает исправления причины. Зависание, неограниченный
   рост ресурсов, ресурсный отказ и функциональная ошибка остаются проблемами,
   даже если внешний бюджет позволяет дольше ждать.
5. Для первого релиза допустимы документированные умеренные задержки редких
   операций с подтверждённым завершением. Новый строгий latency SLA не вводится;
   необязательные оптимизации можно отложить. Незавершающиеся сценарии,
   ресурсные отказы, неограниченный рост ресурсов и нарушения данных,
   replay/privacy остаются блокирующими. Все принятые функции и сквозные
   сценарии сохраняются в объёме поставки и проверок.

## Обоснование

Один чистый локальный прогон уже включает полный `verify`, воспроизводимость
импорта и production E2E, а CI остаётся отдельной проверкой точного кандидата.
Отмена второго обязательного локального `verify` не убирает ни одной проверки.
Обоснование timeout остаётся предметом ревью; принятие задержки редкой операции
не подменяет доказательство её корректности или завершения.

## Последствия

Это решение заменяет только прежнее требование об обязательном отдельном
полном author verify, в том числе в заключительном абзаце ADR 0087.
Старые ADR и handoff-снимки сохраняются; их предметные контракты и фактически
выполненные проверки не переопределяются. Текущие правила опубликованы в
`AGENTS.md` и [проверках CI](../process/ci-checks.md).

При выборе большего case budget отказ может обнаруживаться позже; выбранный
запас не объявляется доказанно достаточным до выполнения теста. Новый процесс
не гарантирует длительность полного CI и не меняет его конфигурацию.
