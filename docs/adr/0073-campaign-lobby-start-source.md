# ADR 0073 — Источник лобби, готовности и первой мирной сцены

- **Статус:** принято владельцем, issue #206
- **Дата:** 2026-11-02
- **Дополняет:** ADR 0006, 0064, 0067–0072
- **Граница:** поставка Atlas и совместимость; runtime — #173, затем #174

## Решение владельца

Все шесть предложений #206 приняты. Новые возможности игрока и мастера
обязательно получают реальные элементы управления на экранных формах.
Наличие workflow-команды без доступного пользователю control не выполняет
приёмку. Поставка Atlas **1.8** сохраняет schemaVersion 1.2.0 и legacy
filenames v1.2: 376 форм, 1697 переходов, 111 workflow, 2448 QA, 1261 CTA.
Предметные реестры и Runtime Pack не изменяются.

Основание механики — AQA-009/016/023, AQ2-006/008/010 (Rules v1.7),
Q-CHAR-009, Q-CAMP-001, Q-GM-001/026/028/030. Исходные механика, группы,
назначения и controller bindings уже сохранены admission runtime.

## Ready и состав

В NET-006 добавлены «Готов» и «Отменить готовность», команда
`UI-CMD-CAMPAIGN-READY-SET`. Хост сначала проверяет весь admitted ACTIVE
состав. Повреждённая механика, blocker у ACTIVE или ошибочный controller
запрещают preflight целиком; недопустимо молча отфильтровать такого героя.
Только явно PROPOSED с blockers остаются вне Ready и сцены.

Готовность устройства относится ко всему его ACTIVE-набору, упорядоченному
по campaignCharacterId. Устройство с ACTIVE и blocked PROPOSED подтверждает
только ACTIVE-набор; интерфейс явно различает эти две части. Устройство
только с blocked copies не может подтвердить Ready. Любая его доказанная
admitted вкладка той же кампании может передать device intent; это не
original-tab-only правило прежнего ACCEPT. Каждая вкладка получает только
свою разрешённую проекцию; blocked вкладка не входит в PLY-001 после Start.

lobbySnapshotRevision меняется при изменении состава, механики, назначений,
controller bindings или подтверждённого начального времени. Это делает
прежнюю готовность недействительной. Отдельная readinessRevision позволяет
другому устройству подтвердить Ready без сброса остальных. Ready допустим
до ввода времени и подтверждает именно отсутствие времени; первый ввод
изменяет основание и требует нового Ready. Без времени запрещён Start.

## Начальное время и Start

NET-016 содержит три обязательных ввода без defaults: dayNumber —
положительное целое, hour 0–23, minute 0–59. Команда
`UI-CMD-CAMPAIGN-INITIAL-TIME-SET` сохраняет начальную отметку до Start.
Виртуальная минута равна `(dayNumber - 1) * 1440 + hour * 60 + minute`;
ввод и итог должны представляться точно безопасными целыми. Переполнение
отклоняется до записи. Часовой пояс и системное время не участвуют.
Технический committedAt квитанции хранится отдельно от игрового времени.

После Start clockMode=STOPPED: автоматический ход требует отдельного
решения мастера по AQ2-006 и не реализуется в #173. dayPhase вычисляется
по AQ2-008/ADR 0006; localLighting не выводится из dayPhase.

`UI-CMD-CAMPAIGN-START` повторно проверяет единственного GM, pre-start PAUSED,
точный актуальный состав и обе ревизии, Ready всех включённых устройств,
время и отсутствие конфликтующей операции. Одна транзакция создаёт одну
мирную сцену, checkpoint и receipt, переводит кампанию в HOSTING и связывает
существующие copies/controllers/groups/location labels. Новые группы,
маркеры, координаты, боевые акторы и localLighting не создаются. Отсутствие
первого Start — отдельный guard; PAUSED после будущей Pause не разрешает
второй Start. Exact replay возвращает прежний результат без отката текущего
состояния, новых IDs, timestamp или повторной сцены.

## Проекции и общая оболочка

CMP-007/GM-001/GRP-001 имеют PRE_START и STARTED_PEACE: до admission допустим
пустой groups[], до Start scene=null. Используются одни campaign/GM authority
и routes, совместные с #187. Арт берётся из existing checksum либо явно
отсутствует; file picker в read-only панели отсутствует. Локация хранится
у каждой copy; разные локации участников одной группы не сводятся к первой.

PLY-001 PEACE_SNAPSHOT строится по текущей доказанной tab/seat binding для
одного собственного героя. HP, характеристики, OE, состояния и постоянные
пассивы берутся из committed AdmissionMechanicalSheetV1. symbionts[] может
быть пустым, temporaryEffects[] не подменяет постоянные состояния. Боевой
контекст отсутствует. Несозданный marker — UNKNOWN/NOT_SET с отсутствием
его identity/revision/координат по смыслу MAP-007, не markerRevision=0.
Глобальная Start receipt, чужие листы/devices и GM-private данные игроку
не передаются. Общий inventory/effects/time/combat engine не добавляется.

До Start панель даёт read-only возврат «Подключение к кампании» в CMP-006
с тем же GM context и подтверждённой creationReceipt, включая нулевой состав.
Оттуда доступны прежние QR и очередь NET-017 с прежним возвратом; переходы
не меняют Ready или время и не создают второй административной оболочки.

## Восстановление и неизменность истории

Тот же аутентифицированный transport восстанавливает admitted bindings до
и после Start. Текущий HOSTING/PAUSED отделён от immutable PAUSED birth.
Нельзя ослабить проверку прежней admission history, приняв более новую
campaign revision на доверии: runtime обязан проверять полную композицию
старого журнала и нового lifecycle continuation. Старые receipts и FINAL
не переписываются, поздний admission этим решением не разрешается.

Точная поставка B3 дополняет B0/B1/B2 из ADR 0071. Разрешены только
явные forward-пары B0→B3, B1→B3, B2→B3 и прежние пары/тождественное чтение.
Manifest и оба Atlas файла B3 закреплены SHA-256; остальные двадцать
артефактов, 24 replay inputs и runtime tuple остаются прежними. Будущие,
обратные и повреждённые поставки не становятся совместимыми автоматически.

## Проверка и границы

Все JSON/Markdown workflow, CTA, transitions, journeys, requirements и QA
зеркала согласованы. Старые guards сохраняются; обновляются только точные
пересекающиеся literals/seals новой поставки. Отдельный seal и mutation
tests защищают Ready, time input, singleton Start, empty/ABSENT варианты,
owner privacy и единую оболочку. Реальные byte fixtures проверяют replay
с прежних поставок без подмены механики или исходных receipts.

Runtime #173 проходит реальные controls → Ready/Unready → Start → GM/player
проекции → reconnect/restart. Blocked copy остаётся в лобби; этот срез не
обещает редактор уже принятой immutable PROPOSED публикации. Проверяются
отказ Ready blocked-only и успешный ACTIVE-набор mixed device согласно
принятому правилу состава. #206 не закрывает runtime #173 или #174.

Перед merge обязательны независимое ревью, полный прогон чистой копии
окончательного SHA (ci/import/verify/import:verify/test:e2e), зелёный CI
того же SHA и сравнение дерева squash с проверенным. Отказы сохраняются.
