# ADR 0058 — Стартовое оружие CHR-022

- **Статус:** принято
- **Дата:** 2026-10-29
- **Реализует:** issue #151
- **Дополняет:** [ADR 0021](0021-roll-model.md),
  [ADR 0025](0025-character-draft-checkpoint-scope.md),
  [ADR 0055](0055-starting-armor-bundle.md),
  [ADR 0057](0057-armor-initial-interactions-and-presentation-recovery.md)

## Контекст

После #146 сохранённая броня имеет один immutable D20 и подписанный следующий
этап `CHR-022`, который ещё не публиковался. Issue #151 добавляет ровно одно
оружие и отдельный D20 качества. Источники: Atlas `CHR-021/022/023/024`,
`AQ2-003`, `CORE-172/173`, `Q-CORE-052`, Item Registry v1.6 — каталог,
профили, поля, формулы, определения боевых значений, instance model и словари.
Настройка профиля, деньги, общий инвентарь и финальное сохранение остаются
следующими задачами.

## Решение

### 1. Адресуемая стадия и совместимость сохранений

Optional `startingWeaponStage` входит в существующий whole-checkpoint. Она
ссылается на подтверждённый armor checkpoint, содержит один
`weaponQualityRollRequestId`, snapshot режима ввода, immutable quality record
и необязательный финальный checkpoint. Outer protocol и SQL-схема не меняются.

Новый armor checkpoint атомарно создаёт pending weapon stage в той же
транзакции. Её entry ссылается на реальный armor request/receipt, без второго
синтетического command. Новый receipt содержит optional
`weaponQualityRollRequestId`; loader сверяет его со стадией и не принимает
подмену pending ID или отсутствие связанной стадии. Исторический receipt
сохраняет прежнюю форму. История не считает общий receipt дважды.

Историческое сохранение #146 без weapon stage остаётся читаемым. Его
`CHR-021::CTA::001` исполняет явный `STARTING_WEAPON_ENTRY` существующей
`UI-CMD-CHAR-WIZARD-CHECKPOINT`: проверяет armor receipt, создаёт один request
и отдельный entry receipt. Это специализация того же нормативного перехода
«bundle receipt committed; owned not equipped». Загрузка и reconnect никогда
не выделяют новый ID. Уже существующая стадия возобновляется presentation-only.

### 2. Точная пара типа и варианта

Loader сверяет 27 canonical `ITM-WPN-001..027` и 29 пар с Item Registry.
`attackVariantId` и словарь `ATTACK_VARIANT` задают `DEFAULT`, фиксированные
хваты полуторного меча `ONE_HAND/TWO_HAND`, `SWORD` Корнадоры и
`SHIELD/RAPIER` Бларадэ. Это адрес профиля; компонентный inventory runtime
не создаётся. Отдельного атакующего `SHIELD` Корнадоры источник не задаёт.
Массивы, объединённые значения, неизвестные и смешанные пары отклоняются.

Atlas `CHR-022::CTA::001` требует для FREE/UNITED формульный профиль, а
`CTA::002` для PURE — canonical fixed. Политики `EXACT_JOINT_FORMULA` и
`TEMPLATE_FIXED` сопоставляются явно. Проверка выполняется до первого броска,
а каталог проекции содержит только совместимые с расой пары: нельзя необратимо
зафиксировать выбор, у которого отсутствует разрешённое продолжение.

PURE по-прежнему не имеет самостоятельного entry из #146. Этот срез не
создаёт обходной composition/equipment checkpoint. Проверка fixed-пути сама
по себе не объявляет PURE wizard доступным.

### 3. Рекомендация и preview

Host строит allowlist preview из требований, навыка/класса и штрафа поставленного
профиля. Для трёх точных формульных литералов техническая запись заменяется
объяснением зависимости силы/ловкости от профиля и фиксированного хвата:
готовые S/D и параметры будущей заявки не подставляются. Неизвестный литерал
отклоняется. Названия вариантов берутся из словаря.
Rule IDs, источники, raw rows, availability trace и GM finalization data не
публикуются, включая идентификаторы внутри текста.

`STARTING_WEAPON_QUALITY` принимает ровно одну пару и один D20. AUTO вызывает
sampler один раз после guards внутри транзакции; MANUAL требует явно введённую
грань 1..20. Используется общая с бронёй поставленная шкала качества.
Рекомендация не задаёт final qualityTier, не меняет параметры, XP или критические
цепочки и не удаляет оружие даже при 1–4. Оружие и броня остаются
`OWNED_NOT_EQUIPPED`.

### 4. Восстановление и граница с профилями

После первого committed display тип, вариант, грань и receipt неизменны.
Safe-return `CHR-022::CTA::003` и resume `CHR-021::CTA::001` меняют только
presentation revision. Они сохраняют armor/weapon records и не создают новых
requests. Хост проверяет текущую signed форму и ревизии, в том числе при
конкурирующей WS-сессии. Post-write validation остаётся внутри SQLite-транзакции.

`STARTING_WEAPON_CHECKPOINT` фиксирует подписанный `CHR-023` или `CHR-024`.
Renderer остаётся на actionless `CHR-022/CHECKPOINTED`: профили не публикуются
до #152. Replay возвращает прежний receipt; refresh/reconnect/restart и повторное
открытие SQLite восстанавливают сохранённые записи без sampler.

## Отвергнутые варианты

| Вариант                                          | Причина отказа                                             |
| ------------------------------------------------ | ---------------------------------------------------------- |
| Создавать request при restore                    | Меняет состояние при чтении и допускает replacement        |
| Менять исторический armor receipt                | Нарушает его неизменность и существующий replay            |
| Принимать любой тип до проверки расы             | Необратимый roll может оставить игрока без следующего шага |
| Подставить первый вариант или готовое требование | Источник не назначает выбор игрока и будущий профиль       |
| Применить качество как модификатор               | Поставленная шкала имеет рекомендательный смысл            |
| Открыть CHR-023/024 сразу                        | Выходит за контракт #151 и ещё не реализованную authority  |

## Последствия

Публикуется одна дополнительная форма CHR-022. Следующий продуктовый срез —
#152, профили оружия; затем #153–#156. Изменения сохраняют существующие
артефакты, импортер, внешний протокол и ограничения проверок.
