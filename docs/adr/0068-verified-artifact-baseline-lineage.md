# ADR 0068 — Проверенная совместимость исторического baseline

- **Статус:** принято; issue #190, предпосылка разрешённой поставки #177
- **Дата:** 2026-10-30
- **Дополняет:** ADR 0063, 0064 и 0067; определение identity baseline не меняется
- **Граница:** совместимость сохранённых данных, без миграции механики или authority

## Контекст

ADR 0063 определяет `baselineVersion` как SHA-256 точных байтов всего
`artifacts/CHECKSUMS.sha256`. Loader проверяет полный состав и каждый файл.
Значение входит в export/archive, admission descriptor и campaign birth proof.
Поэтому разрешённое изменение двух Atlas-файлов в #177 меняет baseline даже
при неизменной механике персонажа. Прямое сравнение старого документа только
с текущим ID отвергнет прежний документ; подстановка нового ID нарушит его
канонические байты, checksum, подпись или исходную квитанцию.

Наблюдаемый baseline B0 поставки Atlas 1.5:
`sha256:4ed1aadbbfffe96b5f90d919c6cb1074a03c9aefddb33dcf094408ad69a0e149`.
Его manifest содержит 22 пути, включая два Atlas-файла и 20 остальных.
Полный reader появился после предыдущих Atlas amendments: их успешные импорты
не являются проверкой совместимости уже сохранённых экспортов и кампаний.

Владелец разрешил новую поставку #177 и сохранение проверяемости существующих
FINAL/checkpoints/proofs. Issue #190 отделяет нужный технический фундамент
от поставки Atlas и незавершённого application runtime #171.

## Решение

### Identity и разрешённая пара поставок

Текущий loader сохраняет прежний полный manifest hash и все проверки файлов.
В кодовую поставку вне `artifacts/` включаются точные исторические manifest
bytes с закреплённым SHA и реестр конкретных разрешённых successors. Для B0
разрешён только сам B0 либо точный B1 из согласованного кандидата #177.
Реестр закрепляет полный ID successor и байты обоих Atlas-файлов, а не только
номер версии или утверждение «поменялся Atlas». Изменённый кандидат требует
явного обновления pin и повторного review.
Неизвестный B2 не получает права проверять B0 через historical context.
При этом прежний loader может проверить B2 как фактический current и
обрабатывать его собственные current документы: это не совместимость с B0.
Pin находится вне хешируемого manifest, поэтому не создаёт цикла хеширования.

Для исторического context проверяются одновременно:

- exact SHA исторического manifest и известный полный текущий successor ID;
- одинаковый полный набор из 22 путей;
- неизменность каждой non-Atlas строки; различаться могут только
  `atlas/Symbiosis_V7_Web_UI_Screen_Atlas_v1.2.json` и одноимённый `.md`;
- exact bytes 24 JSON inputs транзитивного creation replay: 12 character/rules
  и 12 item inputs, включая weapon/money/five-position/finalization каталоги;
- проверенные PASS `registryVersion`, `catalogVersion`, `builtAgainstTuple`;
- неизменность выданного runtime context, включая используемые labels/maps.

Неизвестный ID, поддельный manifest, другой набор путей, non-Atlas byte drift,
иная механика/tuple или изменённый context приводят к отказу. Ни общий prefix,
ни диапазон версий, ни произвольный peer/browser manifest не служат разрешением.

### Current context и исторический context

Loader выдаёт context с module-private authority, недоступной структурной
подстановке. Resolver использует только эту authority и проверенную lineage.
Spread clone, самостоятельно собранный объект или заменённый baseline ID
не дают исторических прав. Historical view сохраняет **исходный** ID и
доказанно совместимые каталоги; это выбор контекста проверки конкретного
документа, а не переименование документа.

Глобальный startup `d.baseline` остаётся фактическим current context.
Проверки filesystem-vs-startup, fresh reload, listener и TOCTOU сохраняют
точное равенство. Историческая совместимость не разрешает hot swap файлов
в работающем процессе. View не превращается в новый current baseline.

### Сохранённые данные и полная проверка

Archive validator выбирает context по исходному document baseline ID;
candidate verifier использует один и тот же проверенный context для schema,
provenance и полного replay. Проверки owner/source/checksum/closed fields
остаются точными. Resolver лишь разрешает попытку проверки, а не объявляет
документ валидным по одному членству ID в реестре.

Stored campaign proof разрешается по той же lineage без изменения birth
receipt, payload, checkpoint или подписи. SQL migration и переписывание
данных не нужны. Новый экспорт использует текущий baseline, а known EXPORT
replay возвращает прежние сохранённые байты. Старые descriptor, witness,
outbox и command IDs не пересоздаются ради смены поставки.

На main этот фундамент обслуживает archive/candidate и применимые readers
сохранённой кампании. Application-only callers PR #185 — peer runtime,
local peer, hosted writer и discovery projection — интегрируются в #171.
SQL writer сохраняет собственную проверку доверенного baseline внутри
транзакции. Ни data lineage, ни подписанный peer не выдают роль, seat,
campaign copy или полномочия preliminary/final admission.

## Обоснование

Полный ID обеспечивает исходную byte identity; совместимость — отдельное
утверждение о конкретных поставках и неизменной механике. Одних строк версии
недостаточно, поэтому закреплены реальные source inputs полного replay.
Одних неизменных non-Atlas строк также недостаточно для blanket compatibility:
принимается только явно зарегистрированный successor, а не любая новая
самостоятельно пересчитанная Atlas-поставка.

Тесты используют точные B0/B1 bytes. Компактный patch fixture воспроизводит
согласованный Atlas из реального предшественника и проверяется SHA до/после;
постоянные тесты не зависят от ignored `reports/`. Разные Node-процессы нужны
для old/new сценария, чтобы singleton-каталоги первого процесса не скрыли
дрейф данных второго. Исходные export/archive/candidate и SQLite receipts
проходят полный replay, reopen/restart и negative cases без подмены ID/crypto.

## Последствия

Разрешённая Atlas-only поставка может сохранять проверяемость старых данных,
не маскируя изменение полного baseline. Каждый successor требует отдельного
seal и проверки; автоматической совместимости будущих поставок нет.
В частности, #186 добавляет новые art artifacts и не удовлетворяет правилу
равного набора путей B0/B1: её lineage обосновывается по фактической поставке.

Исторический snapshot и тестовые fixtures увеличивают кодовую поставку,
но не становятся новым источником игровых правил. Semantic
`graphDigest`/`contentDigest` Atlas остаются историческими полями по ADR 0037/0049;
они не заменяют manifest SHA или проверку совместимости.

Это решение не объявляет завершёнными #177/#171, не обеспечивает произвольную
совместимость разных wire/engine версий и не отменяет независимое чтение,
полные verify/E2E на окончательном SHA и зелёный CI перед каждым merge.
