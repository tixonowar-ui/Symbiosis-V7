# ADR 0061 — Пять произвольных стартовых позиций CHR-037

- **Статус:** принято
- **Дата:** 2026-10-29
- **Реализует:** issue #154
- **Дополняет:** [ADR 0021](0021-roll-model.md),
  [ADR 0025](0025-character-draft-checkpoint-scope.md),
  [ADR 0060](0060-starting-money.md)

## Контекст

После подтверждения рекомендации денег хост подписывает `CHR-037`.
Item Registry `AQ2-003` требует пять позиций, каждая содержит один тип и
положительное количество. Один D20 относится ко всему стеку; описательный
предмет занимает одну позицию. `AQA-012` фиксирует выбор перед броском,
`AQ2-004` сохраняет всё выбранное количество независимо от рекомендации,
`AQ2-005` запрещает свободному тексту самостоятельно влиять на механику.

Атлас задаёт отдельный `ROLL-COMMIT` для выбранного стека, локальное
редактирование, checkpoint пяти receipts и safe-return на `CHR-038`.
Пакет из пяти бросков одной командой не предусмотрен.

## Решение

### 1. Каталог, количество и описательная категория

Выбираются только строки `catalogue` с буквальным `Можно в инвентарь=true`:
62 из 64 поставленных типов. У `RES-MAG-001/002` стоит `UNKNOWN`; неизвестная
возможность хранения не считается разрешением. Прямой выбор этих типов
отклоняется. `AQA-011` допускает любые предметы из базы доступных предметов,
но не устраняет неизвестные значения реестра.

Отдельная поставленная категория `open-catalogue/GEN-010` — «Любой заявленный
стартовый предмет», представление «Свободное описание → согласование мастером».
Она адресует описательную заявку и не становится выдуманным `ItemTypeID` или
механическим экземпляром инвентаря. Другие неизвестные типы не превращаются
в story item. Для `GEN-010` требуется непустое описание; у каталожного типа
описание отсутствует. Внутренние обозначения источников и диагностики в
свободном тексте отклоняются до записи, без отражения текста в ошибке.

`instance-model/quantity` задаёт INTEGER, required, STACK и ограничение ≥1.
Host принимает положительное безопасное целое для каждой позиции, включая
описательную. Ровно пять разных `positionId` обязательны; одинаковый тип
в разных позициях разрешён и не приводит к объединению стеков.

### 2. Независимые запросы и локальный выбор

Пять `positionId` и пять `qualityRollRequestId` связываются с money checkpoint.
Адрес — префикс `five-starting-positions:` и SHA-256 UTF-8 JSON-массива
`["symbiosis.five-starting-positions.v1", characterDraftId,
moneyCheckpointReceiptId, index, kind]`, где index равен 0..4, kind —
`position` либо `quality`. Это технические адреса, не случайность или seed.

Новый money checkpoint атомарно сохраняет pending stage с этими адресами.
Исторический checkpoint без optional stage остаётся неизменным: чтение
выводит те же адреса без записи или allocator, первый roll материализует stage.
Entry заимствует money request/receipt и не учитывает их повторно в истории.
Виртуальные адреса проверяются на коллизии при чтении и перед roll; durable
набор резервирует их после сохранения stage.

До броска выбор живёт в local draft. Каждая отдельная команда передаёт все
пять позиций, выбранный position/request и одну грань MANUAL либо null AUTO.
Host проверяет весь набор до RNG и записи. Команда фиксирует результат только
выбранного стека; прочие выборы сохраняются в полном снимке как редактируемый
черновик. Последующая команда может изменить только ещё не брошенные позиции.
Изменение типа, количества или описания уже зафиксированной позиции отвергается.

### 3. Один D20 на стек, пять разных receipts

AUTO вызывает sampler один раз после guards внутри транзакции; MANUAL
принимает явную грань 1..20 без sampler. Request и receipt каждого стека
различны; порядок независимых бросков может отличаться от порядка позиций.
Exact replay возвращает прежний receipt; changed payload, stale revisions,
чужие адреса и попытка replacement не вызывают дополнительный sampler.

`CORE-173` и словарь QUALITY задают шкалу:

| D20   | Рекомендация           |
| ----- | ---------------------- |
| 1–4   | Отсутствует/непригоден |
| 5–9   | Плохое                 |
| 10–14 | Обычное                |
| 15–18 | Хорошее                |
| 19    | Исключительное         |
| 20    | Редкое                 |

Даже 1–4 не удаляет предметы и не меняет quantity по `AQ2-004`.
Все позиции имеют `OWNED_NOT_EQUIPPED`; характеристик, критических цепочек,
XP, master approval и автоматической экипировки этот срез не создаёт.
AUTO receipts входят в `randomReceiptIds`, MANUAL остаются в полной истории.

Loader воспроизводит каждый шаг, проверяя выбор относительно ранее
зафиксированных позиций, полный снимок, recommendation, IDs, owner и ревизии.
Post-write validation выполняется внутри SQLite-транзакции.

### 4. Presentation и завершение

Safe-return `CHR-037 → CHR-038` сохраняет деньги и все позиции. Возврат
`CHR-038 → CHR-037` использует уже committed money checkpoint и меняет только
presentation revision. Повторный money checkpoint и возврат к изменению
оружия при этом недоступны.

Историческое начальное `CHR-038` с ревизией money receipt продолжается на
`CHR-037`; более поздняя signed presentation сохраняет явный safe-return.
URL и история браузера не назначают экран. Refresh/reconnect/restart и
реальное SQLite reopen не назначают новые IDs и не повторяют броски.

Final checkpoint требует точные пять связей position/request/receipt.
Он подписывает `CHR-032`, сохраняя текущий `CHR-037` actionless.
Player projection состоит из явного allowlist; сырые строки реестров,
Rule IDs, trace и скрытые данные мастера не передаются.

## Последствия

Доступны все восемь имущественных операций создания: armorBundle, оружие,
деньги и пять позиций. Их общая проверка и финальное сохранение остаются
в #155. `CHR-032/025`, общий inventory/equipment runtime и структурирование
story item мастером не реализуются. Артефакты, SQL-схема, outer protocol,
зависимости и конфигурация проверок не меняются.
