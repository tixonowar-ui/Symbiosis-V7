# ADR 0059 — Профили оружия и вход PURE в стартовое имущество

- **Статус:** принято
- **Дата:** 2026-10-29
- **Реализует:** issue #152
- **Дополняет:** [ADR 0025](0025-character-draft-checkpoint-scope.md),
  [ADR 0046](0046-character-starting-skills.md),
  [ADR 0055](0055-starting-armor-bundle.md),
  [ADR 0058](0058-starting-weapon.md)

## Контекст

#151 фиксирует тип, вариант и D20 качества оружия, но ещё не публикует
`CHR-023/024`. #152 продолжает формульную заявку не-Чистого и полный
фиксированный профиль Чистого. У PURE нет random/manual состава: поставленный
Character Registry задаёт `BaseSymbiontSlots=0`, а Atlas требует уже
checkpointed пустой состав перед `CHR-017::CTA::004`. Ограничения входа
ADR 0055 §1–2 и ADR 0058 §2 оставляли этот путь за пределами прежних срезов.

Источники: Atlas `CHR-015/017/019/021/022/023/024/031`, workflow
`UI-CMD-CHAR-WIZARD-CHECKPOINT` и `UI-CMD-PLAYER-WEAPON-REQUEST-SUBMIT`;
`Symbiosis_V7_Item_Registry_v1.6_with_icons.xlsx`, импортированные
`catalogue`, `weapon-profiles`, `weapon-fields`, `combat-values`, `formulas`,
`formula-ranges`, `dictionaries`, `operations`, `rule-trace`; правила
`CORE-183..186/190`, операции `OP-REQ-PLAYER/VALIDATE`; Character Registry
`races`. Новые игровые значения и изменения поставленных артефактов не нужны.

## Решение

### 1. Явный пустой состав PURE на существующем checkpoint навыков

Это точечное расширение ограничений ADR 0055 §1–2 и ADR 0058 §2: завершённый
состав для входа в броню теперь включает explicit `PURE_EMPTY`. Остальные
контракты брони, оружия и качества сохраняются.

При финальном exact-fill `CHR-015::CTA::001` существующая команда checkpoint
атомарно сохраняет навыки, `pureCompositionStage` и pending armorBundle с
одним ID набора и одним ID запроса качества. Общий skill request/receipt
связывает эти записи; история не считает его дважды. Для PURE не назначается
режим получения симбионтов: он остаётся `NOT_APPLICABLE`, random/manual стадии
отсутствуют. Режим ввода D20 качества наследуется из уже подтверждённого выбора.

`CHR-017::CTA::004` остаётся навигацией: проверяет сохранённый пустой состав и
pending armor request, затем показывает `CHR-021`, не выделяя ID. Safe-return
`CHR-021 → CHR-019` сохраняет результаты; `CHR-019` показывает пустой состав
без добавления симбионтов. Возврат через `CHR-017` возобновляет тот же набор.

Исторический финальный skill checkpoint PURE читается без изменений.
Пользователь явно возвращается к `CHR-015` и подтверждает тот же exact-fill
набор. Отдельный reconfirm receipt связывает новый пустой состав и pending
броню; исходный skill receipt остаётся неизменным. Чтение, reconnect и restart
никогда не выполняют эту инициализацию.

### 2. Полный каталог и точное доказательство достижимости

Каталог продолжает 27 типов и 29 пар #151: 22 формульные пары и семь
фиксированных пар шести типов. Он сверяет исходные строки и нормативные
контракты, а не выводит правила из названий. Версия шаблона и
`canonicalProfileVersion` — точный default `ITEM_REGISTRY_V1.2` из
`weapon-fields`; версия файла поставки v1.6 его не заменяет. Для формул
сохраняется `ITEM_FORMULAS_V1.2`.

Игрок явно передаёт `commonWitness={L,Lw,Ls}`, независимые значения каждого
адресованного witness-дайса и все заявленные `formulaOutputs`. Все три уровня
обязательны, целочисленны и неотрицательны; `Lw>0` требуется только там, где он
является делителем. Неиспользуемый символ не получает выдуманного значения.
Верхние игровые пределы не добавляются; ограничения точного числового
представления проверяются отдельно.

Чистый domain разбирает ограниченную грамматику без `eval` и проверяет все
выходы одной формулы на одном общем witness. Порядок вычислений, округление,
минимумы, фиксированный хват и раздельные дайсы берутся из источника.
`formula-ranges` позволяет ранний отказ, но не доказывает достижимость.
Каждый выход должен точно совпасть с заявленным значением.

Это `VALIDATION_ONLY`: приложение не генерирует witness, не бросает
производственные дайсы, не рассчитывает крафт и не создаёт предмет.
`independentManufacturingDiceReceipts` — immutable свидетельства
`PLAYER_WITNESS`, связанные с request, submit command, переменной, размером
дайса и переданным значением. Они не являются AUTO/MANUAL roll receipts,
не вызывают sampler и не пополняют историю физических бросков.

Полный эффективный профиль сохраняет шаблон, runtime-выражения, специальные
свойства и прочие неизменяемые поля. Формульные выходы накладываются только на
разрешённые поля экземпляра. У PURE весь canonical profile read-only;
acknowledge принимает только связанную версию, подмена полей отклоняется.

### 3. Durable стадия, отказы и восстановление

Новый checkpoint `CHR-022` в той же транзакции создаёт один адресуемый
`weaponProfileStage`, привязанный к weapon checkpoint receipt. Историческая
запись без стадии получает её только явным entry через существующий checkpoint;
старый receipt не переписывается. Safe-return `CHR-023/024 → CHR-022` и resume
до отправки меняют только presentation revision.

`INVALID` сохраняет попытку для replay, оставляет заявку `DRAFT` и открывает
`CHR-031` с полями и понятными причинами отказа. Частичный профиль и proof не
сохраняются. Подписанный возврат ведёт на `CHR-023`; отклонённый ввод не
подменяет authoritative данные. Публичная проекция допускает только известные
числовые поля ввода и факты профиля, удаляет внутренние ID также из прозы.

Успех атомарно сохраняет полный профиль, formula proof и witness receipts с
переходами `DRAFT → VALIDATED → SUBMITTED`; формульная заявка получает
`PENDING_GM`. Fixed acknowledge сохраняет canonical профиль с
`NOT_APPLICABLE` для согласования формульной заявки. Оба пути сохраняют
`OWNED_NOT_EQUIPPED`, существующие D20 качества и их рекомендательный смысл.

После успеха изменение или повторная новая отправка запрещены. Точный replay
возвращает прежний receipt. Loader заново вычисляет профиль и proof по каталогу,
проверяет binding, историю, значения witness receipts и уникальность ID.
Post-write validation выполняется внутри SQLite-транзакции. Диалог отказа,
safe-return и успешная стадия восстанавливаются после reconnect/restart без
новых IDs и RNG. Outer protocol и SQL-схема не меняются.

### 4. Граница с последующими задачами

Публикуются `CHR-023/024/031`. После успешной отправки или acknowledge
`CHR-038` подписан как следующий этап, но ещё не публикуется: текущая форма
профиля actionless. Согласование мастером, создание/экипировка inventory item,
деньги, пять произвольных позиций и final save в этот срез не входят.

## Обоснование

Инициализация PURE на существующем финальном checkpoint навыков замыкает
нормативный guard «пустой состав уже checkpointed», сохраняя навигационную
природу `CHR-017::CTA::004`. Это новый контракт хранения, а не новая игровая
механика. Проверка явно предоставленного witness доказывает требуемое
существование общего решения без запрещённых производственных бросков.
Полный профиль и его повторная проверка не позволяют заменить совместную
достижимость набором независимых min/max.

## Последствия

PURE получает сквозной путь к стартовому оружию. Исторические записи требуют
явного продолжения; загрузка не мигрирует их игровое состояние. Canonical
версия v1.2 намеренно отличается от имени workbook v1.6. Следующая очередь —
#153–#156; ограничения предыдущих ADR на изготовление, экипировку и master
override сохраняются. Финальные результаты проверок фиксируются отдельно в
handoff после общего прогона.
