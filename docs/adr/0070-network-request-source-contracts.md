# ADR 0070 — Отдельная библиотека сетевых контрактов заявки

- **Статус:** принято; техническая граница issue #195
- **Дата:** 2026-10-30
- **Дополняет:** ADR 0020, 0067 и 0069
- **Граница:** shared DTO и standalone codecs; прикладной сценарий остаётся в #171

## Контекст

Atlas 1.6 / ADR 0069 задаёт предварительную очередь заявок и два решения GM.
Player draft и GM queue имеют разных владельцев и разные поля. Их общий
контракт нужен обеим сторонам до подключения обработчиков приложения.

Полный #171 включает ещё transport, durable intent, подтверждение текущего
состояния, очередь, решения и восстановление двух установок. Поставка чистой
библиотеки имеет самостоятельную границу и не закрывает этот сценарий.

## Решение

### Закрытые DTO

`device-admission.ts` задаёт player draft/resume и отдельные списки player и
GM workflow IDs. `network-application.ts` описывает NET-001–005/011, CHR-027
и самостоятельную NET-017 GM family. GM projection имеет ровно 12 полей Atlas;
player networkScope/controllerSeat в неё не наследуются.

`network-application-codec.ts` проверяет точный состав полей, enum, UUID,
безопасные целые ревизии, уникальность и порядок кандидатов, согласование
scope/presentation и applied/current revisions. Standalone JSON encoders и
decoders возвращают обычные `EncodeResult` / `DecodeResult`. Неизвестные поля
и значения отклоняются; отказ не отражает исходные строки. Decoders принимают
JSON string без приведения других входов или вызова их пользовательских getters.
Decoders сохраняют безопасные пути известных полей. Standalone encoders
возвращают путь `$` при отказе: предварительный JSON обход может встретить
неизвестное приватное имя поля раньше проверки закрытой формы.
Существующая семантика JSON grammar ADR 0020 сохраняется.

NET-005 включает IN_REVIEW. NET-017 различает PENDING, IN_REVIEW и REJECTED;
CANCELLED отсутствует в текущей очереди. Пустая очередь допустима, одинаковые
отображаемые имена допустимы, идентичность строки задаётся requestId.
ACCEPT-TO-REVIEW и REJECT имеют отдельные закрытые payload и 14-полевую
квитанцию. Проверяется изменение одной request revision и точный порядок
checksums исходного submitted batch; повторная квитанция отделяется от
последующего текущего состояния.

`candidateSnapshotChecksum` player candidate сохраняет смысл FINAL
`sourceChecksum`. `snapshotChecksum` GM summary означает
`descriptor.exportBytesSha256`: SHA-256 всех канонических export-file bytes,
включая поле checksum и завершающий LF. Равенство этих разных хешей не
предполагается. Библиотека проверяет форму и согласованность уже переданных
значений; происхождение bytes проверяет host/store.

### Подключение выполняется отдельным срезом

Core wire v3 unions/dispatch, host vocabulary, capabilities, routes, handlers,
SQLite и клиентское приложение этой поставкой не расширяются. Даже успешно
разобранное standalone сообщение ещё не принимается core decoder. Barrel
exports библиотеки доступны будущим consumers без запуска приложения.

Authority, владение устройством/вкладкой, реальная GM identity, актуальная
кампания, подпись peer, freshness, replay и транзакционная гонка решений
проверяются в #171. Принятый JSON не является доказательством этих свойств.
Настоящие copies/seats/reservations и final admission остаются в #172.

## Обоснование

Состав DTO берётся из поставленного Atlas 1.6 и ADR 0067/0069, а точные
source assertions уже защищены importer/validator. Standalone библиотеку
можно проверить без публикации незавершённого GM пути. Для presentation
tests используются реальные metadata форм и ограниченные известные bindings;
это не включает отсутствующий runtime маршрут.

Граница source contracts → runtime сохраняет полный #171 как единый
пользовательский сценарий. Лимиты PR и конфигурация проверок не меняются.

## Последствия

Появляется отдельный проверяемый consumer API. Положительные и mutation tests
проверяют player/GM изоляцию, пустые/непустые очереди, ревизии, receipts,
редакцию ошибок и неизменность core dispatch. Shared слой не импортирует
Node APIs, host, SQL или filesystem.

В #171 остаются реализация и сквозные доказательства приложения. Его PR #185
нельзя объявлять готовым по наличию этих DTO; перед merge нужны независимые
полные verify/E2E окончательного SHA и зелёный CI.
